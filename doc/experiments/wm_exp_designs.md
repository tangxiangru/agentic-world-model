# Research World Model Design

Goal: learn a world model with **X = (experiment scripts, serving configuration)** and **Y = a statistic computed from ten benchmark runs**, so we can choose experiments worth training. Beat an inference-only LLM with the same evidence. **Current scope: feature engineering and lightweight predictor research, not new PTB/GPU training runs.** Offline improvements do not establish the earlier ≥5% end-to-end RPM goal.

**2026-09-12 next-contract proposal:** [Complete recipe X/Y and construction plan](wm_benchmark_recipe_proposal.md) strengthens X to include every declared dependency needed to build the checkpoint from pinned base assets and evaluate it. It audits the updated HF revision and distinguishes the existing 526 script-bound examples from as-yet-uncounted complete recipes; the existing v1 release remains unchanged.

Use the [concise X/Y design](wm_benchmark_spec.md) to iterate on the input table
and target definition.

**Predictor input boundary:** X contains the final launched training source,
launch arguments/configuration, required resources and patches, plus the serving
specification. The base model is identified by name/revision and loading settings;
its weights are supplied only to the execution environment. “Final” refers to the
source actually launched for the selected checkpoint, not later workspace edits.

The supplied experiment scripts include their bound launch arguments, referenced script configuration, and supplied training/data-building helpers. Serving configuration means the effective generation settings used by the evaluator, including output limits and stop handling. Fix the benchmark, question set and evaluation protocol within each prediction task. Every predictive feature must be derived from X; cards, checkpoint IDs, hashes and outcome-bearing transcripts may support provenance checks but do not add predictive inputs. Measured parent accuracy, prior-best scores and training/evaluation outcomes are outside X. Earlier training scripts contribute only if explicitly included in the supplied experiment scripts.

**Proposed primary Y: mean benchmark accuracy over ten complete runs.** For run r with C_r correct answers on the same N questions:

`Y = (1 / 10) * sum_{r=1}^{10}(C_r / N)`.

This is one scalar label per script/config example. The ten runs repeat benchmark evaluation of one realized checkpoint; they do not measure variation from retraining the scripts. Preserve the per-question/per-run correctness matrix so other targets, such as run-to-run variability or per-question success rates, can be defined explicitly. The target statistic must be fixed before model comparison. Mean accuracy differs from pass@10 (at least one successful answer per question); improvement over a measured parent would require that parent's runs as additional label evidence. Missing or failed runs remain incomplete rather than being dropped or scored as zero.

## Experiment Matrix

The pinned HF matrix now contains **3,000 result files** (1,980 development and 1,020 reserved-test), spanning 516 checkpoint IDs. These are source-record counts; distinct weights and benchmark eligibility are audited separately in [benchmark v1](wm_benchmark.md).

The measurement matrix is **checkpoint weights × effective generation configuration**. Each matrix cell is one `exp_id`, with ten benchmark runs supplying Y. Bind its checkpoint to the experiment scripts to construct X; weights themselves are not an input to the predictor. Re-serving archived weights supports retrospective script/config prediction; claims about choosing genuinely untrained experiments require predictions frozen before those experiments run.
