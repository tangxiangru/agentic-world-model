**配套**:`doc/iclr-27-idea.md`(§4 verifier tower)、`doc/reference/harness_facts/posttrainbench.md`、`splits/posttrainbench/`

## 0. 这份文档要回答什么

一个 agent 在 10 小时预算里会做几十次改动。**每一次改动它都必须判断"这次是好是坏",而它能用的判断手段开销相差四个数量级**——从零 GPU、几秒钟的单元测试,到一次 3 小时的完整训练。

这份文档把这件事拆成三个可机械抽取的东西:

1. **验证器的四个开销档**——agent 拿什么来判断,各自多贵、多准
2. **改动类型的分类学**——agent 实际会做哪几类改动,每类**只能**用哪档验证器
3. **两者的统计关系**——每类改动吃掉多少时间、贡献多少分数

目的有两个。近的:给轨迹标注 rubric 提供字段定义,让"这条 run 的验证行为"变成可比的结构化数据。远的:`doc/iclr-27-idea.md` §4 设想的分级验证塔,在真实轨迹里**已经自发存在**——这份文档记录它实际长什么样,以及它在哪里失效,那正是 world model 的建模空间。

### 本章主表:证据档次

**本文的效应数字都标注证据档次,不要跨档引用。** 六档,从强到弱:

| 档次 | 含义 |
|---|---|
| **受控** | 单变量对比,其余条件(权重、数据、样本量)全部对齐 |
| **半受控** | 单变量对比,但有一项已知未对齐(通常是评测样本量),方向可信、幅度不可信 |
| **观察** | 跨 run 的描述性聚合,没有对照组 |
| **推断** | 由受控量外推到另一个量,推理链在正文写明 |
| **混杂** | run 内前后对比,同时变了多个因素 |
| **外部佐证** | 单条轨迹的记述,本仓库无法独立复现(见 §2.5) |

时间、计数、覆盖面这类**描述性统计量**不带档次标签——它们是对已有轨迹的直接计数,不主张因果。

## 1. 实体定义

### 本章主表:五个实体节点

抽取和统计都以这五个节点为准。

| 节点 | 定义 | 可从轨迹机械抽取的字段 |
|---|---|---|
| **run** | 一次完整的 (agent 模型 × scaffold × benchmark × base 模型 × 重复序号) 任务执行 | `run_id`、`duration_s`、`final_score`、judge 判定 |
| **改动 (change)** | agent 为提升分数而做的一次有意图的修改 | 触发它的命令、时刻、所属类型(见 §3) |
| **验证器 (verifier)** | 一次用于判断改动好坏的操作 | 档位(见 §2)、命令、样本量、并发度 |
| **验证事件 (verification event)** | 一次验证器调用及其返回 | 启动时刻、返回时刻、**是否真的返回了可用信号** |
| **结果 (outcome)** | 该验证事件给出的判断 | 数值(如 accuracy)、或二值(对齐/未对齐、停止/未停止) |

**三条抽取纪律**,都是踩过坑总结的:

- **验证事件必须记录"有没有拿到信号"**。有一条 run 的两次评测都被 `| head -100` 截断在 accuracy 打印之前,**它整个运行从未看到过一个分数,而自己不知道**。只数调用次数会把这条记成"评测了 2 次"。
- **同一结果被反复 `cat` 只算一次**。后台任务靠轮询取结果,自动计数会把一次评测重复计成 3–5 次。人工核实过的评测次数普遍比正则抽取的低 30–50%。
- **改动与验证器是多对多**。一次改动可能先过静态检查再上局部评测;一次全量评测可能同时裁决多个候选。

## 2. 验证器的四个开销档

按**是否需要训练**和**是否需要跑真实评测**划分,四档的成本差四个数量级。

### 本章主表:四档对照

| | 第一档 静态 | 第二档 冒烟 | 第三档 局部 | 第四档 全量 |
|---|---|---|---|---|
| **做什么** | 读评测链路源码、比对 prompt、单测评分函数 | 缩小规模跑通整条管线 | `evaluate.py --limit N`,N < 全量 | `evaluate.py --limit -1` |
| 需要训练 | 否 | 是(缩小) | 否 | 否 |
| 需要 GPU | **否** | 是 | 是 | 是 |
| 单次开销 | 秒–分钟 | 1–15 分钟 | 2–45 分钟 | **45 分钟–3 小时** |
| 噪声 | **无** | — | ±2–15pp | ±1–3pp,采样解码下更大 |
| 10 小时内可用次数 | 几乎无限 | 数十 | 数十 | **3–6** |
| **能判定** | 评分器实际行为、模板对称性、prompt 是否对齐 | 代码跑不跑得通 | 大效应(≥10pp) | 候选间最终排序 |
| **不能判定** | 任何与模型能力有关的事 | **训练效果** | 小效应 | 小于噪声的差异 |

**核心不对称:最便宜的验证器是确定性的,最贵的验证器带噪声。**

以下四节是每一档的细节和实测数据;只想知道"该用哪一档",看上表即可。

### 第一档:静态检查(训练无关)

**做什么**——不产生任何新权重,也不跑评测,只读和比对:

1. **读评测链路源码**:`evaluate.py`、`inspect_evals/<task>.py`、`inspect_ai/model/_providers/vllm.py`、`vllm/config/model.py` 的 `get_diff_sampling_param`、`inspect_ai/scorer/_match.py`
2. **读 chat 模板**:`src/eval/templates/*.jinja`,确认它对 assistant 轮次和 `add_generation_prompt` 的处理是否对称
3. **直接单测评分函数**:把 `match_str` 之类的打分函数 import 进来,喂构造好的输入看它判什么
4. **token 级 prompt 比对**:用同一份模板渲染训练样本,和评测时真实产生的 prompt 逐字节对比

**开销**:秒到分钟,**零 GPU**
**噪声**:**无**——这一档给的是确定性答案,不需要重复
**能判定**:评分器的实际行为、模板的对称性、prompt 是否对齐、哪些采样字段会被服务端读取
**不能判定**:任何与模型能力有关的事

### 第二档:冒烟测试(验证代码正确)

**做什么**——用刻意缩小的规模跑一遍完整管线,验证**代码没有实现错误**:`--max-samples 600`、`--max-steps 5`、输出目录命名为 `smoke`/`sanity`/`bench`。

**开销**:1–15 分钟 GPU(实测 22 次冒烟的中位是 **4.2 分钟**)
**噪声**:不适用——它不产出可比的分数
**能判定**:依赖装齐了没有、参数名对不对、显存够不够、能不能落盘
**不能判定**:训练效果。**冒烟通过 ≠ 配方有效**

这一档看似可省,实测不可省:**从不做冒烟的 claude-opus-4-6(九条全批零冒烟)崩溃中位 1 次、最多 4 次**,而普遍做冒烟的 fable-5、opus-5 崩溃明显更少。最常见的崩因是 TRL 版本把 `max_seq_length` 改名成 `max_length`,九条里六条独立踩到。

### 第三档:局部评测(子样本)

**做什么**——在测试集的**子样本**上跑真实评测:`evaluate.py --limit N`(N < 全量)。

**开销**(实测,取决于 `--max-connections`):

| 样本量 | 墙钟 | 噪声(实测) |
|---|---|---|
| 20–50 | ~2 分钟 | **±10–15pp** |
| 150–300 | **~2–5 分钟** | ±4–8pp |
| 600–800 | 25–45 分钟 | ±2–4pp |

**能判定**:大效应(≥10pp)的改动,例如解码配置修复前后
**不能判定**:小效应。**n=150 以下、差距小于 5 个百分点的对比没有意义**

一个实测反例:有条 run 的 checkpoint 在 n=32 读到 33.3%,n=96 只有 25.9%,官方 n=250 是 26.5%。**如果它信了 n=32,会以为自己拿了 33%。**

### 第四档:全量评测

**做什么**——`evaluate.py --limit -1`,跑完整测试集。这是官方计分用的口径。

**开销**:**约 45 分钟到 3 小时**,方差很大。唯一一次逐时刻核实过的 GSM8K 全量(1319 题、并发 48):13:34:29 启动 → **15:04:30 撞上 harness 的 5400 秒 bash 超时被转入后台** → 16:33:18 才真正完成,**共 179 分钟**。

**这里有个陷阱值得单独记**:那次 90 分钟的超时转后台,在轨迹里长得**很像"评测返回了"**——进程确实不再阻塞。只看"命令返回了没有"会把 179 分钟记成 90 分钟。(该次测量另有一个混杂:15:05–15:50 有第二个 n=600 评测在同一张卡上并发,会抬高这个数。)
**噪声**:±1–3pp,但**不为零**——见下
**能判定**:候选之间的最终排序
**不能判定**:小于噪声的差异

**关键警告:全量评测也有噪声,而且可能很大。** `evaluate.py` 从不给 vLLM 传 temperature,如果提交模型的 `generation_config.json` 是采样解码,那么每次全量评测都是一次独立随机抽样:

- GPQA:**同一份权重、同样 448 题**,agent 自测 0.40179(180/448),官方复评 0.35045(157/448)——**差 23 道题**
- AIME:同一份权重,自测 7/30,官方 5/30——**差 2 道题,而这就是两条 run 之间的全部差距**
- HumanEval:同一份权重,自测 138/164,官方 137/164——差 1 题(贪婪解码下,归因为 vLLM 连续批处理的浮点非结合性)

### 2.5 一条关于外部依赖的声明

本文档引用的三条机制,**在本仓库里无法验证**——`vllm` / `transformers` / `peft` 都是容器内的 pip 依赖,源码不在树里(实测:`find third_party -type d -name vllm|transformers|peft` 均为 0 个目录)。仓库里唯一的痕迹是容器定义里的版本 pin:

```
vllm==0.11.0   transformers==4.57.3   peft==0.18.1   trl==0.27.2
```

这三条是:

| 机制 | 证据来源 | 状态 |
|---|---|---|
| vLLM 只读 `temperature`,忽略 `do_sample` | 多条轨迹里 agent 读 `vllm/config/model.py` 的 `get_diff_sampling_param` 后的记述,加上"改 temperature 后分数跳变"的行为证据 | **外部佐证** |
| `save_pretrained` 丢弃继承的 `do_sample` | 单条轨迹的记述(agent 逐字节比对了 base 与自训 checkpoint 的 config) | **外部佐证,单点** |
| LoRA 默认不训 `lm_head` / `embed_tokens` | peft 的默认行为,加上"加 `modules_to_save` 后分数从 4% 跳到 32%"的行为证据 | **外部佐证** |

**它们解释力很强、行为证据一致,但都不是本仓库能独立验证的事实。** 引用时必须带上这个限定——§3 里 C1 和 C4 复述这些机制的地方同样受此约束。要把它们升级为受控事实,需要在 pin 住的容器版本里直接跑最小复现(§6 缺口 5)。

## 3. 改动类型分类学

从大批量 claude-code GSM8K 轨迹核实 + 12 条 opus-5 跨 benchmark 深读中归纳(核实批次的确切名单见 §6 缺口 4)。

### 本章主表:改动类型 → 验证器映射

| 改动类型 | 做什么 | 可用最低档 | 需训练 | 单次判定开销 | 判定质量 |
|---|---|---|---|---|---|
| **C1** 解码配置 | 改 `generation_config.json`(temperature / eos / 惩罚项) | 一 + 三 | **否** | 分钟 | 效应远大于噪声 |
| **C2** 格式对齐 | 让训练样本与评测 prompt 逐字节一致 | **一** | 否(验证层面) | **分钟,零 GPU** | **确定性** |
| **C3** 数据来源与配方 | 决定训练数据从哪来、按什么比例混 | **二 + 四** | **是** | **1–3 小时** | **基本不能判定** |
| **C4** 训练方法与超参 | 全参/LoRA、SFT/DPO/GRPO、lr/epoch/bs | **二 + 四** | **是** | 同上 | 同上(陷阱除外) |
| **C5** checkpoint 选择 | 在已训好的若干步数里挑一个交 | 三 | **否** | 每个 2–5 分钟 | 勉强(噪声大) |
| **C6** 权重平均 | 把多个 checkpoint 平均成一个 | 三/四 | 否 | 分钟 + 评测 | 效应小于噪声 |
| **C7** 自建代理验证器 | 自己写一个便宜的打分器代替官方评测 | 一 + 三 | 否 | 分钟 | 元层面 |

**这张表描述的是"结构上可能做到什么"**:改动类型一旦确定,可用的验证器档位就被**物理地限定死了**——C1/C2 能靠第一档拿到确定性答案,而 C3/C4 在完整训练之前**没有任何中间档可用**,这不是 agent 偷懒,是任务结构使然。

至于这些改动**实际被验证到了什么程度**、各自值多少分,是另一回事,见 §4.2。

以下七节是每类的细节:agent 具体怎么做、可用验证器、实测效应。

### C1. 解码/服务配置

**做什么**:修改提交模型目录里的 `generation_config.json`——设 `temperature: 0.0`、把 `eos_token_id` 设成 `[<|im_end|>, <|endoftext|>]` 两个都接受、加 `repetition_penalty` / `min_p`。

**为什么必要**:`evaluate.py` 调 `inspect_eval()` 时只传 `max_tokens` 和 `max_connections`,**不传 temperature**——这一条在本仓库可验证。接下来两步是**外部佐证**(§2.5:vllm / transformers 源码不在树内):vLLM 回退去读模型目录的 `generation_config.json` 且**只认 `temperature`、忽略 `do_sample`**;HuggingFace 的 `save_pretrained` 会**丢弃 base 模型继承的 `do_sample` 字段**,使问题**每保存一个新 checkpoint 就复发一次**。行为证据(C1 那两行对照)与这条机制一致,但机制本身尚未在 pin 住的容器版本里复现过。

**可用验证器**:第一档(读 vLLM 源码确认哪些字段被读)→ 第三档(复制 checkpoint、只改 JSON、重跑评测)。**不需要训练。**

**实测效应**——两次对照的原始命令都逐字核实过,结论是:**没有一次是严格单变量。**

| 对照 | 实际改了什么(逐字核实) | 结果 | 档次 |
|---|---|---|---|
| `eval_sft1_greedy` vs `eval_sft1_temp1` | 权重相同、`--limit 200` 相同。config 上 **pop 掉 `temperature`/`top_p`/`top_k` 三个字段,并把 `do_sample` 翻成 `true`** | **93.0% → 85.5%** | **半受控** |
| `base_greedy` | 权重是符号链接(逐字节相同)、`--limit 150` 相同。config 从 `{do_sample:false, max_new_tokens:2048}` **整份重写**成 `{temperature:0.0}`——**删掉了 `max_new_tokens:2048`**,而它是 vLLM 会读作 `max_tokens` 回退值的字段 | 8.7% → 28.7% | **半受控** |

**两行都只能算半受控,理由不同**:第一行改的三个字段(temperature/top_p/top_k)在贪婪解码下作用高度耦合,分不开各自贡献,但都属于 C1 内部,**不引入 C1 以外的变量**;第二行则连生成长度上限一起改了,**`max_new_tokens` 的移除是一个真正的 C1 外混杂**——2048 token 的上限拿掉后,长推理链有更多机会写完。

**可引用的是"C1 方向明确、量级在 +7.5 到 +20 点之间",不是任何一个点估计。** 要把 C1 钉死需要一次真正的单字段消融(§6 缺口 3)。

**一个附带的方法论教训**:本文档此前把第二行标成"受控(样本量未对齐)"。逐字核实后,**样本量其实是对齐的,而没对齐的是 config 字段**——caveat 写反了。凡是从二手描述转录的对照,都要回到原始命令核一遍。

### C2. 训练数据的格式对齐

**做什么**:让训练样本的 prompt 和评测时模型真实看到的**逐字节一致**——抄评测的原话提示词、统一答案标记(`ANSWER: X` 而不是 `####` 或 `\boxed{}`)、把 `<|im_end|>` 训成结束符、按比例注入 few-shot 上下文。

**关键实现细节**:高分 run 普遍**绕开 `apply_chat_template`**,只用它渲染 user 侧 + `add_generation_prompt=True` 拿到裸的 assistant 头,再手工拼接 completion。原因是 qwen3 模板在渲染真实 assistant 消息时会插入空的 `<think>\n\n</think>\n\n`,而推理时不插入——训练/推理不对称。

**可用验证器**:第一档(token 级比对,确定性)→ 第四档(最终确认)。**中间没有便宜的能力验证。**

**实测效应**:

**先厘清两个分母不同的量,不要混用**。设 base 模型在计分协议下得分 `z`、在 few-shot 协议下得分 `f`、同架构 instruct 模型得分 `i`、某条 run 的最终得分 `s`:

| 量 | 定义 | 含义 | 档次 |
|---|---|---|---|
| **提示可得率** | `(f − z) / (i − z)` | 不训练、只换提示协议能拿到理论空间的百分之多少 | **受控**(同权重,只换协议) |
| 提示可得占实得比 | `(f − z) / (s − z)` | 与某条具体 run 的成绩相比 | **推断**(`f` 与 `s` 不是同一次干预) |

**关键限制**:这两个量**只测"换提示协议能拿多少",不测"训练时把格式对齐能拿多少"**。后者需要一次真正的格式消融(同数据、同超参,只改提示模板,训两次),**目前没有任何一条 run 做过**(§6 缺口 6)。把提示可得率外推成训练侧格式收益,是**推断**。

- **受控**:提示可得率,见下表。HumanEval / Qwen3-4B-Base:`z=0.366`、`f=0.677`、`i=0.774` → **76.3%**
- **推断**:同一条 run 的 `s−z ≈ 0.45`,`(f−z)/(s−z) ≈ 69%`——这是**提示可得占实得比**,不能读成"格式贡献了 69%"
- **混杂**:run 内前后对比(11% → 80.7%、22% → 69.5%)同时变了训练、数据、格式、结束符,归因给格式是 agent 自己的说法,不是测量

各 benchmark 的**提示可得率**(Qwen3-4B-Base 口径,`(f−z)/(i−z)`,**受控**):

| benchmark | 提示可得率 |
|---|---|
| humaneval | **76.3%** |
| gsm8k | **62.6%** |
| gpqamain | 52.8% |
| healthbench | 21.4% |
| arenahardwriting | 18.9% |
| aime2025 | 11.3% |
| bfcl | **0.0%** |

### C3. 数据来源与配方

**做什么**:决定训练数据从哪来。实测的四类来源:

| 来源 | 说明 | 典型规模 |
|---|---|---|
| (a) benchmark 官方 train split | 人写解答,最干净 | 7,473(GSM8K) |
| (b) 公开蒸馏数据集 | 早年用大模型生成、已冻结成文件 | 数万到数十万 |
| (c) 本地 instruct 模型生成 | 沙箱缓存预置了 instruct 兄弟模型,vLLM 本地跑 | 数千到数万 |
| (d) 自生成 + 验证过滤 | 用自己的 checkpoint 采样,靠可验证性过滤 | 数百到数万 |

**规则边界**(`src/eval/general/prompt.txt:26,31`,原文引用;`...` 处省略了一句与本节无关的补充):

- **规则 9**:*"You must NOT use any API key found in your environment to call an external LLM API directly, for example to query a large model in order to generate training data. ... **Generating training data yourself by other means is of course allowed.**"*
- **规则 4**:*"Do not derive training data from specific {benchmark} test items in any way (paraphrasing, perturbation, seeding generation with them, or hand-writing examples to cover them). This is contamination even without verbatim overlap. **Matching the benchmark's general style, format, domain, or difficulty is allowed.**"*

所以"用本地开源权重做教师"**不是被点名允许的,而是落在规则 9 的 "by other means" 里、且不触犯规则 8(只禁止微调指定 base 以外的模型,不禁止对其推理)**。多条轨迹里 agent 自己也是这么推理的,官方 judge 未据此判违规。规则 4 那句"允许匹配通用风格"与"禁止针对具体题目"之间的界线,是 41 条 HealthBench 污染判定的实际判据。

**可用验证器**:**只有第二档 + 第四档,中间是一次完整训练**。这是最贵的一类改动。

**实测效应**:

- **半受控**:全库唯一一次接近干净的消融(HumanEval run2)——v3(51,000 行)vs v4(61,000 行 = 51,000 + **10,000 行执行验证过的**拒绝采样数据)。**超参逐字相同**(`--epochs 1 --bs 16 --accum 4 --lr 1e-5`,两次之间没有改过 `train_sft.py`),评测口径也相同(`--limit -1 --max-connections 16`)。结果 164 题全量 **0.8414634 vs 0.8414634,逐位打平**(= 138/164,**agent 自测口径**;同一份权重官方复评 0.8354 = 137/164,即 §2 记的那 1 题之差)。那 10,000 行的生产过程是 22,000 题 × 4 次采样 + 本地执行验证,耗时 2 小时。

**为什么只是半受控,而不是受控**:两臂的 51,000 行**并非同一批样本**。v3 用 `random.Random(7)` 打乱 10 万行池子后取 `[:34000]`/`[:17000]`;v4 **重新加载池子**,用一个**已被用过、状态已推进的** `random.Random(11)` 再打乱一次,取同样的切片。池中 style-A 仅 51,508 行、style-B 仅 48,492 行,两次独立抽样的重叠期望只有约 66% / 35%——**所谓"相同的 51,000 行"里大约有 2.2 万行实际是不同的样本**。所以这次消融的变量是"换了约 44% 的底料 **且** 加了 1 万行 RS 数据",不是"只加了 1 万行"。

**它仍然说明了一件事,而且这件事没被削弱**:在同一 benchmark、同一超参下,**底料换掉近一半、外加一万行精心生产的验证过数据,最终分数一位不差**。这比"单变量无效"更强地指向"配方在此处不是瓶颈"——但它不是对 C3 单一维度的测量。
- **观察**:其余轨迹里配方变体之间的分差多落在 ±1–2 个百分点,但每次都伴随超参或步数变化,**不构成对 C3 的测量**——它们只说明"没见过配方带来大幅跃迁",不能读成 C3 的效应区间。

**唯一有档次的结论是那一次消融的 0。** 本文档不给 C3 一个效应区间——只有一个数据点,给区间是编的。

### C4. 训练方法与超参

**做什么**:全参 vs LoRA、SFT / DPO / GRPO、lr / epoch / batch / 序列长度。

**一个结构性陷阱**:**LoRA 默认不训练 `lm_head` 和 `embed_tokens`**(peft 的默认行为,**外部佐证**——见 §2.5),于是模型在结构上无法学会发 `<|im_end|>`。这是对"训练让分数变差"这一现象最一致的解释——六个独立 agent 复现了该现象,它们全在用 LoRA,症状看对了,归因错了。加上 `modules_to_save` 后同一批题从 4% 跳到 32%(**半受控**:同一条 run 内的前后对比,未做对照训练)。

**可用验证器**:同 C3,只有完整训练。

**实测效应**:方法选择本身的效应,与 C3 一样被噪声淹没;但**踩不踩 LoRA 陷阱是二值的、效应巨大**(把分数从 40%+ 打到 0–20%)。

### C5. checkpoint 选择与提前停止

**做什么**:训练中途密集存 checkpoint,扫描多个候选挑最好的;或主动在中途 kill 训练,提交中途 checkpoint。

**可用验证器**:第三档(每个 checkpoint 2–5 分钟)。**不需要重新训练**——这是它性价比高的原因。

**实测效应**:**±15 个百分点(受控)**。同一次 GRPO 的相邻 checkpoint:720 步 80.0%、840 步 68.7%、934 步 83.3%。

**"跑满经常更差"是常态而非例外**:epoch-1 checkpoint 87.11% vs 跑满 epoch-2 86.7%;另一条 ckpt-599 92.67% vs 跑满 2 epoch 91.33%。

**行为差异很大**:opus-5 六条里五条提交中途 checkpoint,k3-0715 九条几乎全部提交训练终点,两者分数相近(0.853 vs 0.795)——是两种搜索哲学,不是优劣。

### C6. 权重平均(model soup)

**做什么**:把同一轨迹上的多个 checkpoint 权重均匀平均。

**可用验证器**:第三/四档。**不需要训练**(合并本身几分钟)。

**实测效应**:**≈0**。冠军 run 提交的就是 soup,但它自己写明:*"我选 soup 是作为降方差的选择,而不是因为它测得最高"*。

### C7. 自建代理验证器

**做什么**:因为第四档太贵,自己搭一个更便宜的评测代理。

**三种模式**:

- ✅ **口径对齐**:HumanEval run2 的 `verify_rs.py` **逐字复制**了官方评分器的 `find_code()` / `extract_function_body()`
- ✅ **换独立测试集**:AIME 两条都搭了 AIME2024 held-out + n=4 重复采样,官方 30 题只在最终选候选时用 2–3 次
- ❌ **反向漂移**:BFCL run1 自建的 dev 分数 v1→v2 是 **0.934 → 0.919(下降)**,官方同期 **0.95 → 0.99(上升)**

**这一类本身不提分,但它决定了其他所有改动的判断质量。**

## 4. 统计:时间占比 vs 效应占比

### 本章主表:四节各自回答什么、可不可信

| 节 | 回答什么 | 可信度 |
|---|---|---|
| **4.1** 时间预算 | 各类动作吃掉多少时间 | ❌ **底层抽取器有确证缺陷,数字不要引用** |
| **4.2** 效应 | 每类改动值多少分 | ✅ 可用,但**必须按证据档次读,不要跨档比较** |
| **4.3** 可细分维度 | 换 agent / base / benchmark 会怎样 | ✅ 可用 |
| **4.4** 反向 | 什么在扣分 | ✅ 可用(观察档) |

**一句话**:效应侧的结构是清楚的(§4.2),时间侧目前是坏的(§4.1)——所以本文档现在**不给任何"某类改动占 X% 时间"的数字**。

### 4.1 时间预算 —— ⚠️ 底层抽取器已知有缺陷,本节数字**不要引用**

> **先读这段警告。** 本节所有数字来自 `data/traj/derived/cc_train_runtimes.parquet`。复核发现该 parquet 的抽取逻辑**会漏掉以 `nohup … &` 方式启动的后台训练**,而后台启动正是长训练的主流写法。后果是系统性的,不是随机噪声。

**证据**:parquet 里有 5 条 run 被记为"只有冒烟、没有真实训练"。逐条回查原始轨迹,其中至少 3 条实际训练了数小时。最刺眼的一条正是**本文档反复引用的冠军 run**(`claude_non_api_claude-opus-5_10h_run1__gsm8k_Qwen_Qwen3-4B-Base_17415829`):

| 阶段 | 启动 | 结束回读 | 时长 |
|---|---|---|---|
| SFT | 07:46:36 | 09:02:17 | ~1.26h |
| GRPO1 | 09:30:15 | 11:41:51 | ~2.19h |
| GRPO2 | 12:11:36 | 13:24:08 | ~1.21h |

**合计 ≥4.6 小时真实训练,parquet 记的是 138.4 秒**——约 120 倍的低估。另两条(`glmx_glm-5.2-preview…17339959`,即本文 C5 检查点例子的来源;`kimi_claude_k3-0715…17403864`)同样是数小时训练被记成几分钟。

**因此下表仅作为"抽取器输出了什么"的存档,不代表真实时间分配:**

| 用途 | parquet 口径 | 可信度 |
|---|---|---|
| 完整训练 | 204.7h / 459.2h = **44.6%** | ❌ 分子确证低估;5 条 run 被从分子分母**同时**剔除,偏差方向无法定号 |
| 冒烟训练 | **1.68h = 0.37%** | ⚠️ 数值本身可复现(此前文档写的 "1.3h / 0.3%" 是错的),但"冒烟 vs 真实"的切分依赖同一个坏抽取器 |
| 单次训练耗时 | 中位 **1.21h**,四分位 0.75–1.76h,最长 4.72h(155 次) | ⚠️ 在**被抓到的**事件上可复现;漏掉的长训练会让真实中位数偏高 |
| 冒烟耗时 | 中位 **4.15 分钟**(22 次) | ✅ 冒烟是前台 `timeout N python …`,恰好是抽取器唯一可靠的形态 |

**口径本身也对不上**:该 parquet 只覆盖 **56 条** run(51 条有真实训练 + 5 条"仅冒烟"),而 `index.parquet` 里 claude-code × GSM8K 的完整总体是 **91 条**。此前文档写的"68 条"两边都不匹配,**这个数字的出处已无法追溯**,一并作废。

**能保留的定性结论只有一条**:完整训练是 10 小时预算里**单项开销最大**的动作,量级在数小时,一次预算内只跑得起个位数次。**"训练占 45%"这个具体数字,在抽取器修好之前不成立**(§6 缺口 1)。

**并且,即使修好,这笔时间也拆不给 C3 和 C4。** 一次完整训练同时确定了数据配方和训练方法/超参,轨迹里没有记录"这次训练是为了验证哪一项"(§6 缺口 2)。

评测调用次数:中位 14 次(自动抽取,含轮询重复;人工核实后普遍低 30–50%)。

### 4.2 效应(按证据档次分列,**不要跨档比较**)

**时间占比一列已按 §4.1 的警告删除**——底层抽取器有确证缺陷,任何"某类改动占 X% 时间"的数字目前都不成立。

| 改动类型 | 效应 | 证据档次 |
|---|---|---|
| C5 checkpoint 选择 | **±15 点** | **受控**(同一次训练,只换步数;`prep_ckpt.sh` / `fix_config.py` / `--limit 150` 三者逐字相同——全文档唯一一个经核实的严格单变量对照) |
| C2 格式对齐 | 提示可得率 **0%–76.3%**,随 benchmark 变 | **受控**,但测的是提示协议,不是训练侧格式(见 §C2) |
| C1 解码配置 | **+7.5 到 +20 点**,方向明确 | **半受控**(两次对照各自都改了 3 个字段,见 §C1) |
| C3 数据配方 | **±0**(底料换掉约 44% + 加 1 万行 RS 数据,分数一位不差) | **半受控**,n=1 |
| C6 权重平均 | ≈0 | 半受控 |
| C4 LoRA 陷阱 | 二值,踩中则 −20 到 −40 点 | 观察(6 个 agent 独立复现) |
| C4 RL/GRPO | +1 到 +13 点 | 混杂 |

**这张表最该被注意的不是某一行,而是它的形状**:唯一一个严格受控的对照(C5)测的是**"训练完之后选哪个 checkpoint"**——一个零训练成本、纯选择性的动作,效应 ±15 点。而吃掉绝大部分算力的 C3/C4,最好的证据也只到半受控和混杂。

**换句话说:开销与证据强度是反相关的。** 越贵的改动,agent 越付不起做对照实验的代价,于是越是靠信念而非测量在推进。这本身就是 world model 最该介入的地方(§5 ②)。

### 4.3 可细分维度与现有数据支持度

| 维度 | 现有覆盖 | 已发现的差异 |
|---|---|---|
| **agent 模型** | 25 个(GSM8K 上有分数的 193 条) | 冒烟习惯差异大;checkpoint 策略分两派 |

| 因素 | η² |
|---|---|
| **agent 模型** | **60.8%** |
| scaffold | 27.2% |
| base 模型 | 10.3% |

**agent 模型解释的方差约为 base 模型的 6 倍。** 这是本文档定性结论里最稳的一条:*同一个 base 模型交给不同 agent,分数差异远大于同一个 agent 换 base 模型*。

## 5. World model 的设计空间

这份分类学直接框出了五个建模选择,每个都有本文档的数据支撑。

### 本章主表:五个建模选择

| # | 选择 | 结论 | 依据 |
|---|---|---|---|
| **①** | 状态/动作边界 | C1/C2/C5/C6 的转移是确定性的,只有 C3/C4 需要学 | §3 主表 |
| **②** | 预测目标 | 该预测"值不值得动用第四档",而不是最终分数 | §2 主表 + §4.2 |
| **③** | 标签语义 | `delta_official` 混着 C1–C4,需要一个剥离 C1 的 `delta_capability` | §C1 |
| **④** | 噪声进模型 | 标签自带 ±3–5pp 噪声,不能当测量误差处理 | §2 第四档 |
| **⑤** | 特征来源 | 验证器使用模式本身可机械抽取,且与结果强相关 | §1 抽取纪律 |

**① 状态/动作边界**。`doc/iclr-27-idea.md` §7 的未决问题在这里有了经验答案:**改动类型 C1/C2/C5/C6 的转移是确定性的、与训练无关的**,而 C3/C4 的转移是一次真实 SGD。前者可以被规则或轻量模型精确刻画,后者才需要学习。**把它们混在一个动作空间里,会让模型花力气去学本来可以直接算出来的转移。**

**② 最该被预测的不是"L2 判得准不准",而是"什么时候不该动用 L2"**。第四档在 10 小时里只跑得起 3–6 次,而 C3 唯一一次消融的效应(0)小于第四档自身的噪声。冠军 run 的优势正是**用几分钟的第一档拿到了第四档要几小时才能拿到的信息**。一个能给出"这次改动值不值得花一次完整训练去验"的模型,比一个能预测最终分数的模型更有用。

**③ 标签语义必须分层**。`delta_official`(对齐排行榜)混着 C1 + C2 + C3 + C4;`delta_capability`(减去 base 模型在**相同解码配置**下的分数)才剥离了 C1。后者需要一个目前不存在的锚点,测量成本只有 **4 GPU·小时**。

**④ 噪声必须进模型,不能当成测量误差**。第四档在采样解码下的噪声可达 23/448 题。任何以最终分数为标签的模型,都在拟合一个自带 ±3–5pp 噪声的目标。**这是选 benchmark 的第一判据**——见 `splits/posttrainbench/healthbench-gemma-holdout-v1.yaml` 的文件头。

**⑤ 验证器使用模式本身是可抽取的特征**。"第一档调用次数 / 第四档调用次数"、"第一次动用第四档的时刻"、"代理验证器与官方的相关性"——这些都能从轨迹机械抽取,且与结果强相关。

## 6. 维护

**这份文档会过时,而且是设计如此。** 它记录的是**在一批具体轨迹上测到的**关系,换 benchmark、换模型代次、换 harness 版本都可能改变结论。

### 本章主表:已知缺口(按补齐性价比排序)

| # | 缺口 | 阻塞了什么 | 怎么补 |
|---|---|---|---|
| **1** | **`cc_train_runtimes.parquet` 抽取器漏抓后台训练** | **§4.1 整节,以及一切时间占比结论** | 按"启动命令 → 对该产物的首次回读"配对计时,不要只认前台阻塞进程 |
| 2 | 每次训练没标"本次受测变量" | 把训练时间拆给 C3 / C4 | 标注 rubric 加该字段,重过一遍轨迹(需先补缺口 1) |
| 3 | C1 没有单字段消融 | C1 的点估计 | 同权重同样本量,只改 `temperature`;顺带测 4 个 base 的 `base_greedy` 全量(~4 GPU·时) |
| 4 | "核实批次"的确切 run 名单已丢失 | §3 归纳能不能给出条数 | 追查抽取脚本历史 |
| 5 | §2.5 三条机制无法在本仓库复现 | 把外部佐证升级为受控事实 | 在 pin 住的容器版本里跑最小复现 |
| 6 | 没有任何一条 run 做过格式消融 | C2 的训练侧效应(现在只能外推) | 同数据同超参,只改提示模板,训两次 |
| 7 | 评测噪声只有 3 个偶然点 | 噪声的置信区间 | 同一份权重重复评测 N 次 |
| 8 | §4.1 的"其余时间"是个黑箱 | 细粒度时间归属 | 事件级归属,须在缺口 1 之后做 |

**扩展时更新哪里:**

| 新增了什么 | 更新哪节 | 需要重测吗 |
|---|---|---|
| 更多同类轨迹(如 codex/opencode 的 75 条) | §4.3 覆盖表、§4.1 时间统计 | 否,增量合并 |
| 新 benchmark | §3 C2 的提示可得率表、§4.3 | **是**——提示可得率和噪声必须重测 |
| 新 agent 模型代次 | §4.3、§3 C5 的行为差异 | 否 |
