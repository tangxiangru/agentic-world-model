## 0. 这份文档要回答什么

一个 agent 在 10 小时预算里会做几十次改动。**每一次改动它都必须判断"这次是好是坏",而它能用的判断手段开销相差四个数量级**——从零 GPU、几秒钟的单元测试,到一次 3 小时的完整训练。

这份文档把这件事拆成三个可机械抽取的东西:

1. **验证器的四个开销档**——agent 拿什么来判断,各自多贵、多准
2. **改动类型的分类学**——agent 实际会做哪几类改动,每类**只能**用哪档验证器
3. **两者的统计关系**——每类改动吃掉多少时间、贡献多少分数

目的有两个。近的:给轨迹标注 rubric 提供字段定义,让"这条 run 的验证行为"变成可比的结构化数据。远的:`doc/iclr-27-idea.md` §4 设想的分级验证塔,在真实轨迹里**已经自发存在**——这份文档记录它实际长什么样,以及它在哪里失效,那正是 world model 的建模空间。

### 本章主表:证据档次

**本文的效应数字都标注证据档次,不要跨档引用。** 六档,从强到弱:

| 档次 | 含义 |
|---|---|
| **受控** | 单变量对比,其余条件(权重、数据、样本量)全部对齐 |
| **半受控** | 单变量对比,但有一项已知未对齐(通常是评测样本量),方向可信、幅度不可信 |
| **观察** | 跨 run 的描述性聚合,没有对照组 |
| **推断** | 由受控量外推到另一个量,推理链在正文写明 |
| **混杂** | run 内前后对比,同时变了多个因素 |
| **外部佐证** | 单条轨迹的记述,本仓库无法独立复现(见 §2.5) |

时间、计数、覆盖面这类**描述性统计量**不带档次标签——它们是对已有轨迹的直接计数,不主张因果。

## 1. 实体定义

### 本章主表:五个实体节点

抽取和统计都以这五个节点为准。

| 节点 | 定义 | 可从轨迹机械抽取的字段 |
|---|---|---|
| **run** | 一次完整的 (agent 模型 × scaffold × benchmark × base 模型 × 重复序号) 任务执行 | `run_id`、`duration_s`、`final_score`、judge 判定 |
| **改动 (change)** | agent 为提升分数而做的一次有意图的修改 | 触发它的命令、时刻、所属类型(见 §3) |
| **验证器 (verifier)** | 一次用于判断改动好坏的操作 | 档位(见 §2)、命令、样本量、并发度 |
| **验证事件 (verification event)** | 一次验证器调用及其返回 | 启动时刻、返回时刻、**是否真的返回了可用信号** |
| **结果 (outcome)** | 该验证事件给出的判断 | 数值(如 accuracy)、或二值(对齐/未对齐、停止/未停止) |

**三条抽取纪律**,都是踩过坑总结的:

- **验证事件必须记录"有没有拿到信号"**。有一条 run 的两次评测都被 `| head -100` 截断在 accuracy 打印之前,**它整个运行从未看到过一个分数,而自己不知道**。只数调用次数会把这条记成"评测了 2 次"。
- **同一结果被反复 `cat` 只算一次**。后台任务靠轮询取结果,自动计数会把一次评测重复计成 3–5 次。人工核实过的评测次数普遍比正则抽取的低 30–50%。
- **反向的偏差同时存在,而且按 agent 族不对称**。`for step in 100 200 300; do python evaluate.py …; done` 是**一个事件、三次评测**,抽取器记一行。全语料低估 **10%**,但 **codex 16% / claude-code 1%** —— 把评测打包进 shell 循环是 codex 的习惯。`eval_events` 的 `n_calls` 列记这个数(按该事件打印出的分数个数;一次都没打印时取下界 1)。**因此评测次数不可跨族比较。**
- **改动与验证器是多对多**。一次改动可能先过静态检查再上局部评测;一次全量评测可能同时裁决多个候选。

## 2. 验证器的四个开销档

按**是否需要训练**和**是否需要跑真实评测**划分,四档的成本差四个数量级。

### 本章主表:四档对照

| | 第一档 静态 | 第二档 冒烟 | 第三档 局部 | 第四档 全量 |
|---|---|---|---|---|
| **做什么** | 读评测链路源码、比对 prompt、单测评分函数 | 缩小规模跑通整条管线 | `evaluate.py --limit N`,N < 全量 | `evaluate.py --limit -1` |
| 需要训练 | 否 | 是(缩小) | 否 | 否 |
| 需要 GPU | **否** | 是 | 是 | 是 |
| 单次开销 | 秒–分钟 | **中位 0.7 分钟** | 1–5 分钟 | **中位 2.5 分钟**(healthbench 19) |
| 噪声 | **无** | — | ±2–15pp | ±1–3pp,采样解码下更大 |
| 10 小时内可用次数 | 几乎无限 | 数十 | 数十 | **数十**(实测中位 4–6 次,最多 111) |
| **能判定** | 评分器实际行为、模板对称性、prompt 是否对齐 | 代码跑不跑得通 | 大效应(≥10pp) | 候选间最终排序 |
| **不能判定** | 任何与模型能力有关的事 | **训练效果** | 小效应 | 小于噪声的差异 |

**两条不对称。** 其一:最便宜的验证器是确定性的,最贵的带噪声。其二,而且更要紧:**四档验证器全都以分钟计,而被它们验证的一次训练以小时计**——瓶颈从来不在尺子,在候选。

以下四节是每一档的细节和实测数据;只想知道"该用哪一档",看上表即可。

### 第一档:静态检查(训练无关)

**做什么**——不产生任何新权重,也不跑评测,只读和比对:

1. **读评测链路源码**:`evaluate.py`、`inspect_evals/<task>.py`、`inspect_ai/model/_providers/vllm.py`、`vllm/config/model.py` 的 `get_diff_sampling_param`、`inspect_ai/scorer/_match.py`
2. **读 chat 模板**:`src/eval/templates/*.jinja`,确认它对 assistant 轮次和 `add_generation_prompt` 的处理是否对称
3. **直接单测评分函数**:把 `match_str` 之类的打分函数 import 进来,喂构造好的输入看它判什么
4. **token 级 prompt 比对**:用同一份模板渲染训练样本,和评测时真实产生的 prompt 逐字节对比

**开销**:秒到分钟,**零 GPU**
**噪声**:**无**——这一档给的是确定性答案,不需要重复
**能判定**:评分器的实际行为、模板的对称性、prompt 是否对齐、哪些采样字段会被服务端读取
**不能判定**:任何与模型能力有关的事

### 第二档:冒烟测试(验证代码正确)

**做什么**——在烧掉几小时之前确认**代码没有实现错误**。它有**两种形态**,前者显眼、后者此前被整个漏掉:

1. **独立冒烟跑**:刻意缩小规模跑一遍完整管线(`--max-samples 600`,输出目录叫 `smoke`/`sanity`/`bench`)。
2. **折叠进正式启动的早期失败探测**:直接启动真实训练,同时挂一个 `until grep -q "examples:" train.log || grep -qiE "error|traceback|OutOfMemory"` 的监视器,在前 60 秒内判定死活。

**开销**:实测 186 次冒烟,**中位 0.7 分钟**,四分位 0.4–6.6 分钟,**无一超过 30 分钟**(口径见 §4.1)
**噪声**:不适用——它不产出可比的分数
**能判定**:依赖装齐了没有、参数名对不对、显存够不够、能不能落盘
**不能判定**:训练效果。**冒烟通过 ≠ 配方有效**

这一档看似可省,实测不可省:**从不做冒烟的 claude-opus-4-6(九条全批零冒烟)崩溃中位 1 次、最多 4 次**,而普遍做冒烟的 fable-5、opus-5 崩溃明显更少。最常见的崩因是 TRL 版本把 `max_seq_length` 改名成 `max_length`,九条里六条独立踩到。

**但"必须有独立冒烟跑"这个更强的说法是错的**,而且此前的抽取口径把它掩盖了。一名标注者给出反例:一条 **零冒烟且零崩溃** 的 run——六次训练全部一次成功落盘,没有一条 traceback / OOM / pkill——它靠的是把探测折叠进正式启动。按产物名和 `--max-samples` 判定冒烟的口径**看不见这种形态**,于是会把这条 run 误分类成"危险的零冒烟 run"。

**语料实测(234 条 run)**:

| | 条数 | 占比 |
|---|---|---|
| 有独立冒烟跑 | 118 | 50% |
| 有折叠式早期失败探测 | 91 | 39% |
| 两者都有 | 41 | 18% |
| **两者都没有** | **66** | **28%** |

**按旧口径判为「零冒烟」的 116 条里,50 条(43%)其实做了折叠式探测。** 所以这一档的正确表述是**「必须有某种早期失败探测」**,而不是「必须有独立的冒烟跑」;真正裸奔的是那 28%,不是那 50%。§4.1 的冒烟时长统计只覆盖第一种形态,第二种的成本本来就摊在真实训练的头 60 秒里,不单独计时。

### 第三档:局部评测(子样本)

**做什么**——在测试集的**子样本**上跑真实评测:`evaluate.py --limit N`(N < 全量)。

**开销**(实测,取决于 `--max-connections`):

| 样本量 | 墙钟 | 噪声(实测) |
|---|---|---|
| 20–50 | ~2 分钟 | **±10–15pp** |
| 150–300 | **~2–5 分钟** | ±4–8pp |
| 600–800 | 25–45 分钟 | ±2–4pp |

**能判定**:大效应(≥10pp)的改动,例如解码配置修复前后
**不能判定**:小效应。**n=150 以下、差距小于 5 个百分点的对比没有意义**

一个实测反例:有条 run 的 checkpoint 在 n=32 读到 33.3%,n=96 只有 25.9%,官方 n=250 是 26.5%。**如果它信了 n=32,会以为自己拿了 33%。**

### 第四档:全量评测

**做什么**——`evaluate.py --limit -1`,跑完整测试集。这是官方计分用的口径。

**开销:中位 2.5 分钟。** 不是小时。取全部**前台**全量评测(墙钟就是 `tool_use`→`tool_result`,无关联歧义),n=784:

| benchmark | 题数 | n | 中位 | 四分位 | 最长 |
|---|---|---|---|---|---|
| bfcl | — | 151 | **1.6 分钟** | 1.4–1.9 | 4.8 |
| humaneval | 164 | 31 | 2.2 分钟 | 2.0–4.1 | 9.4 |
| aime2025 | 30 | 374 | 2.5 分钟 | 1.9–4.9 | 19.4 |
| **gsm8k** | **1319** | 143 | **3.0 分钟** | 2.7–3.4 | 22.4 |
| gpqamain | 448 | 44 | 3.5 分钟 | 1.7–5.4 | 9.6 |
| healthbench | — | 41 | **19.1 分钟** | 17.5–22.3 | 51.7 |

**这一节的档位归类此前是错的,已重算。** 判档位需要知道 benchmark——`--limit 30` 是 GSM8K 的一个子样本,却是 **AIME 2025 的全集**——而生成骨架时没把 benchmark 传给抽取器。修好之后(`eval_events.benchmark_of()` 从 run_id 解析),**第四档评测从 312 次变成 1,285 次**,档位未知的从 974 降到 219。

重算后的数字:

| | 修正前 | **修正后** |
|---|---|---|
| 第四档评测次数 | 312 | **1,285** |
| 前台可计时的 | 784 | 920 |
| 单次中位 | 2.5 分钟 | **2.5 分钟**(四分位 1.7–5.0) |
| 超过 45 分钟 | 2 次(0.3%) | **39 次(4.2%)** |
| 每条 run 发起次数中位 | 4–6 | **2** |
| **一次都没发起的 run** | 6 | **64 / 234 = 27%** |
| **一次全量分数都没拿到的 run** | — | **80 / 234 = 34%** |

**中位 2.5 分钟这个结论稳住了**,四分位也没动。变的是尾巴和覆盖面:超过 45 分钟的比例被低估了 14 倍,而**超过四分之一的 run 从头到尾没有在完整测试集上量过一次**——这远比原来记的 6 条严重,并且直接影响 §5 那条"第四档很便宜、agent 也跑得很勤"的推论:便宜是真的,跑得勤不是。

**本节此前写的"≥90 分钟,常拿不到结果 / 10 小时内 3–6 次"是错的,而且是同一个错误犯了两次。** 它来自一个病态离群值:

| 时刻 | 那条 GSM8K 全量评测发生了什么 |
|---|---|
| 13:34:29 | `run_eval.sh … -1 48` 启动 |
| 15:04:30 | 撞上 harness 的 5400 秒 bash 超时,被转入后台 |
| 15:04:34–15:04:52 | agent 连查三条通道找分数(空 json、满屏 500、inspect_ai 日志 `scores=[]`)——都没有 |
| **15:05:05** | **agent 亲手 `pkill` 杀掉** |
| 16:33:18 | 第二次 pkill,后台任务对象此刻才被回收,harness 标记 `completed` |

第一次我把 `completed` 读成"评测完成",得出 179 分钟;第二次核实了它从未产出分数,改成"≥90 分钟、常拿不到结果"——**但仍然是拿一个离群值当档位属性**。同一条 benchmark 的中位数是 3.0 分钟,四分位 2.7–3.4。那次之所以异常,是它在与别的进程抢同一张卡。

**这条更正改变了 §5 的结论方向,不是削弱它。** 全量评测既然便宜又充裕,那么 C3/C4 验证不足**就不是因为验证器贵**——而是因为**被验证的东西贵**。一个候选要几小时训练才能造出来,量它却只要三分钟。稀缺的是候选,不是尺子。

**噪声**:**不是档位属性**,是「题数 × 解码温度」的函数——见下
**能判定**:候选之间的最终排序
**不能判定**:小于噪声的差异

**关键警告:全量评测也有噪声,而且可能很大。** `evaluate.py` 从不给 vLLM 传 temperature,如果提交模型的 `generation_config.json` 是采样解码,那么每次全量评测都是一次独立随机抽样:

- GPQA:**同一份权重、同样 448 题**,agent 自测 0.40179(180/448),官方复评 0.35045(157/448)——**差 23 道题**
- AIME:同一份权重,自测 7/30,官方 5/30——**差 2 道题,而这就是两条 run 之间的全部差距**
- HumanEval:同一份权重,自测 138/164,官方 137/164——差 1 题(贪婪解码下,归因为 vLLM 连续批处理的浮点非结合性)
- **并发度也会动分数,而且这不属于噪声**:同一份 `final_model`、同样 150 题、同样贪婪解码,只差 `--max-connections`(8 vs 默认 2)→ 0.9133 vs 0.9267。另一条 run 的同一份权重(sha256 逐字节相同)在并发 16 与 4 下读到 **0.4700 与 0.7582,差 28.8 点**。**agent 会有意去改这个参数**,所以它是一类改动(C12)而不是测量误差——放在噪声名下会低估它。

#### 噪声的实测分布(缺口 7 已补)

标注者在轨迹里找到多组**同权重、同评测口径、逐字相同命令**的重复评测。每组都由权重的 sha256 或 `cp -r`/硬链接来源背书:

| benchmark | n | 解码 | 重复读数 | 极差 |
|---|---|---|---|---|
| aime2025 | 30 | 贪婪 t=0.0 | 三对全部 1/30 → 0/30 | **3/3 不可复现**,每次 3.3pp |
| aime2025 | 30 | t=0.6 采样 | 1/30, 4/30, 2/30, 4/30, 1/30 | **10.0pp** |
| aime2025 | 30 | t=0.4 采样 | 2/30, 1/30, 0/30 | 6.7pp |
| humaneval | 150 | t=0.2 采样 | 44.0 / 54.0 / 54.7 / 53.3 / 54.0 | **10.7pp** |
| humaneval | 150 | t=0.1 采样 | — | 2.0pp |
| humaneval | 150 | t=0.05 采样 | — | 0.7pp |
| humaneval | 150 | 贪婪 | 75 / 77 / 77 | 1.3pp |
| gsm8k | 1319 | t=1e-06 | 0.645 / 0.629 / 0.632 | 1.6pp |
| gsm8k | 1319 | t=1e-06(逐字节相同副本) | 0.6368 / 0.6353 | 0.15pp |
| gsm8k | 150 | 贪婪 | 0.78 / 0.7933 | 1.33pp(2 题) |
| gsm8k | 150 | 采样 | 0.5667 / 0.600 | 3.33pp(5 题) |

**四条结论,每条都推翻了此前的一句话:**

1. **「±1–3pp」在 aime2025 上根本不可表达。** 全量只有 30 题,**一道题就是 3.33pp**,不存在 1–3pp 这个刻度。把噪声写成档位属性是范畴错误——它由题数定下界。
2. **噪声随温度单调收缩**:humaneval 上 10.7 → 2.0 → 0.7pp(t=0.2 / 0.1 / 0.05)。所以「采样解码下更大」是对的,但幅度差一个数量级,不能当成一个区间引用。
3. **贪婪不等于确定性。** humaneval 上两次同权重贪婪评测总分都是 77,但 **150 条 completion 里有 33 条不同、4 题判定翻转**——总分相同不代表跑出了同一件事。aime2025 上三对贪婪重复**全部**翻了(1/30 → 0/30)。
4. **把 temperature 压到 `_SAMPLING_EPS` 以下也不等于贪婪。** 有条 run 逐字打印了 pin 版本的 `_SAMPLING_EPS = 1e-05` 并据此把导出写成 `temperature: 1e-06`,同一份 reflink 副本在逐字相同的命令下仍读到 0.645/0.629/0.632(n=1319,极差 1.6pp),而同批权重的严格贪婪导出读到 0.628。

**实践后果**:这条 run 的十几次全量对比里,**所有小于 1 点的差距都小于同权重重复的波动**;而多条 run 的最终提交决策正是建立在这种量级的差距上(0.823 vs 0.807、0.520 vs 0.513、0.8267 vs 0.8400)。


### 2.5 一条关于外部依赖的声明

本文档引用的三条机制,**在本仓库里无法验证**——`vllm` / `transformers` / `peft` 都是容器内的 pip 依赖,源码不在树里(实测:`find third_party -type d -name vllm|transformers|peft` 均为 0 个目录)。仓库里唯一的痕迹是容器定义里的版本 pin:

```
vllm==0.11.0   transformers==4.57.3   peft==0.18.1   trl==0.27.2
```

这三条是:

| 机制 | 证据来源 | 状态 |
|---|---|---|
| vLLM 读 `generation_config.json` 的一组采样字段,`do_sample` **不在**其中 | 三条 run **逐字打印了 pin 住版本(vllm 0.11.0)的 `get_diff_sampling_param` 源码**,`available_params` 含 `temperature / top_k / top_p / min_p / repetition_penalty / max_new_tokens`,不含 `do_sample` | **观察(源码原文,非转述)** |
| `save_pretrained` **只写与库默认不同的字段** | 三条 run 的**原始 config 全文**(非转述),覆盖两个方向 | **观察,机制已定,n=3** |
| LoRA 默认不训 `lm_head` / `embed_tokens` | peft 的默认行为,加上"加 `modules_to_save` 后分数从 4% 跳到 32%"的行为证据 | **外部佐证** |

**第一条比原来写的宽,而且多出一个后果。** 文档此前写的是「只认 `temperature`」——那是不完整的。同一份源码原文里 `available_params` 还含 `repetition_penalty` 与 `max_new_tokens`,两者都有受控的行为证据:一条 run 用逐字节相同的权重(`cp -r`)、逐字相同的评测命令,只设 `repetition_penalty=1.05`,截断从 23 降到 18、自然终止从 7 升到 12;另一条打印出源码里的这一行——

```
diff_sampling_param["max_tokens"] = diff_sampling_param.pop("max_new_tokens")
```

**也就是说 `generation_config.json` 里的 `max_new_tokens` 会成为服务端的 `max_tokens` 默认值。** 「默认值」这三个字要紧:`get_diff_sampling_param()` 返回的是**请求没指定时才生效**的那一套。一名标注者给了反例——同一份带 `max_new_tokens: 16000` 的 config,`--max-tokens 4096` 那档 total time 2:48,16000 那档 18:21,**显式传的值赢了**。两边不矛盾:config 里的值管的是 `evaluate.py` 没传时的情形。 这把「整份重写顺手删掉 `max_new_tokens`」从一条无害的记账差异变成了一个真实杠杆:那条 run 的同一份 grpo1 权重,无上限时 0/30,加了 4096 上限并设 temperature 0 之后 3/30,**是它全程唯一有效的提分动作**。

**第二条已经从「单点转述」升级。** 三名标注者报了表面矛盾的结果:两条 run 里 base 的 `do_sample` 在自训 checkpoint 中消失,第三条(gemma-3-4b-pt)里它连同 `top_k: 64` / `top_p: 0.95` 完整保留。两边的**原始 JSON 都在轨迹里**,不是记述。

矛盾是假的,一个机制同时解释两边:**`GenerationConfig.save_pretrained` 走 `to_diff_dict()`,只序列化与库默认不同的值。** transformers 的 `do_sample` 默认是 `False`——

- base 写着 `do_sample: false` → 等于默认 → **被省略**(消失的那两条);
- base 写着 `do_sample: true` + `top_k` + `top_p` → 都非默认 → **原样保留**(gemma 那条)。

第三名标注者还给出了同一条 run 内的双向对照:agent 把 `do_sample` 设成 `false` 存出后字段不见了,改设成 `true` 再存,字段又出现。**所以「丢字段」不是 bug,是差分序列化;判断某个 checkpoint 会不会丢,看的是那个值是否等于库默认。**

**还有第三态,比「不在」更贵:显式写成 `null`。** 一条 run 的 `generation_config.json` 里 `temperature` / `top_k` / `top_p` 三项都是 JSON null,vLLM 拿不到值就回落到自己的默认(采样)。把这三项改写成真值后,**逐字节相同的权重、逐字相同的评测调用,150 题上 0.460 → 0.613(+15.3 点)**——是那条 run 全程最大的杠杆。所以核查一份提交配置时,「字段在不在」不够,还要看它**是不是 null**。

**丢字段还有第三条路,与前两条都无关:Trainer 自己在存盘前对齐。** 一条 run 的 base 是 `eos_token_id: [1, 106]`,而每次训练 Trainer 都打印 `model config and generation config were aligned accordingly … Updated tokens: {'eos_token_id': 1}` —— **在存盘之前就把它压成了标量**。所以核查一份 checkpoint 的 config 时,`save_pretrained` 的差分序列化、agent 自写的落盘路径、Trainer 的对齐,三条都要考虑。

**但反过来推不成立。** 一名标注者给了反例:某条 run 里 `temperature: 0.0`(非默认值)照样消失了,原因不是 `save_pretrained`——是 agent 自己给合并脚本加的「保存前归一化」把它一并抹掉了。所以这条规则只约束 `save_pretrained` 本身的行为;**看到字段消失不能反推它等于库默认**,还要先确认这一步走的是 `save_pretrained` 而不是 agent 自写的落盘路径。

**其余两条解释力很强、行为证据一致,但都不是本仓库能独立验证的事实。** 引用时必须带上这个限定——§3 里 C1 和 C4 复述这些机制的地方同样受此约束。要把它们升级为受控事实,需要在 pin 住的容器版本里直接跑最小复现(§6 缺口 5)。

## 3. 改动类型分类学

从大批量 claude-code GSM8K 轨迹核实 + 12 条 opus-5 跨 benchmark 深读中归纳(核实批次的确切名单见 §6 缺口 4)。

### 本章主表:改动类型 → 验证器映射

| 改动类型 | 做什么 | 可用最低档 | 需训练 | 单次判定开销 | 判定质量 |
|---|---|---|---|---|---|
| **C1** 解码配置 | 改 `generation_config.json`(temperature / eos / 惩罚项) | 一 + 三 | **否** | 分钟 | 效应远大于噪声 |
| **C2** 格式对齐 | 让训练样本与评测 prompt 逐字节一致 | **一** | 否(验证层面) | **分钟,零 GPU** | **确定性** |
| **C3** 数据来源与配方 | 决定训练数据从哪来、按什么比例混 | **二 + 四** | **是** | **1–3 小时** | **基本不能判定** |
| **C4** 训练方法与超参 | 全参/LoRA、SFT/DPO/GRPO、lr/epoch/bs | **二 + 四** | **是** | 同上 | 同上(陷阱除外) |
| **C5** checkpoint 选择 | 在已训好的若干步数里挑一个交 | 三 | **否** | 每个 2–5 分钟 | 勉强(噪声大) |
| **C6** 权重平均 | 把多个 checkpoint 平均成一个 | 三/四 | 否 | 分钟 + 评测 | 效应小于噪声 |
| **C7** 自建代理验证器 | 自己写一个便宜的打分器代替官方评测 | 一 + 三 | 否 | 分钟 | 元层面 |
| **C8** 运行时/可行性修复 | 让管线跑得**起来或跑得动**:OOM 降 batch、装依赖、绕参数互斥、清磁盘、补缺失的 config 文件,以及纯吞吐优化(`eager → flash_attention_2`) | 二 | 否 | 分钟 | **二值或吞吐**(不做则不跑,或只是更慢) |
| **C9** 提交守卫 | 不改任何产物,只决定此刻把哪个已有候选写进 `final_model` | — | 否 | 秒 | 无验证器 |
| **C10** 合规/去污染 | 过滤疑似泄漏样本、审计训练数据 | 一 | 否 | 分钟 | 确定性(命中数) |
| **C11** 验证器工装 | 把官方评测器的**输出**转成可决策信号:题号集合、截断率、停止原因、重复取均值 | 一 | 否 | 分钟,零 GPU | **确定性** |
| **C12** 验证器口径 | 改官方评测器**自己的调用参数**:`--max-connections`、`--max-tokens`、`--limit`、显存占比。**不碰产物** | — | 否 | 秒 | **它改的是分数本身**(实测 0 → 91 点,三种机制,见 §3 C12) |
| **C13** 跨 run 知识外化 | 写 harness 的持久 memory、NOTES.md,把结论留给后续 episode | — | 否 | 秒 | 对本 run 效应**结构上为 0** |
| **C14** 交付完整性自检 | 对 `final_model` 做机械断言:分片 sha256、config 字段、离线可加载 | 一 | 否 | 分钟 | 确定性,期望效应 0 |
| **C15** 白盒机制探针 | 直接读模型内部量(下一 token 分布、embedding norm)定位失败机制 | — | **需 GPU 但不训练** | 秒到分钟 | **确定性,零噪声** |
| **C16** 权重手术 / 非均匀合并 | 带权插值(含负外推)、单独缩放某几行 `lm_head`、张量级挑选 | 三/四 | 否 | 分钟 + 评测 | 见下 |
| **C17** 候选销毁 | 删掉唯一已训好的候选,或主动中止一次跑得好好的实验 | — | 否 | 秒 | 无验证器 |
| **C18** 重复评测测方差 | 对**逐字节相同**的权重,用**生效参数相同**的调用重跑官方评测器,买的是标准误不是判定 | 四 | 否 | 每次一次全量评测 | **它测的是尺子本身的抖动** |

**这张表描述的是"结构上可能做到什么"**:改动类型一旦确定,可用的验证器档位就被**物理地限定死了**——C1/C2 能靠第一档拿到确定性答案,而 C3/C4 在完整训练之前**没有任何中间档可用**,这不是 agent 偷懒,是任务结构使然。

至于这些改动**实际被验证到了什么程度**、各自值多少分,是另一回事,见 §4.2。

**C8–C17 是标注新增的**,C12–C17 来自 69 条轨迹(独立提出的 run 数:**C12 21 条**、C13 11 条、C14 与 C16 各 5 条、C17 4 条、C15 3 条;门槛 ≥3)。

**C12 是这批里最要紧的一个,因为它改的不是模型,是尺子。** 21 条 run 独立提出它,而本文档此前把这类效应记在 §2 的"噪声"名下——那是误置:噪声是随机的,而这是 agent **有意**改的,且效应远大于噪声:

| 实测 | 同一份权重、同一批题,只改评测调用 | 效应 | 解码 |
|---|---|---|---|
| gsm8k 全量 1319 题(同权重) | `--max-connections` + `--gpu-memory-utilization` | **65.5 点**(0.2146 vs 0.8696) | 采样 |
| gsm8k 全量(权重 sha256 逐字节相同) | `--max-connections` 16 vs 4 | **28.8 点**(0.4700 vs 0.7582) | 采样 |
| humaneval n=50 vs 150(同权重,四次复现) | `--limit` 50 vs 默认 150 | **+26 ~ +29 点**(四次一致) | 贪婪 |
| gsm8k n=150 | `--max-connections` 8 vs 2 | 1.3 点 | 贪婪 |
| gsm8k n=150(同权重) | `--max-connections` 16→2 + `--max-tokens` 800→4000 | **0 点**(读数逐位相同,含 stderr) | 贪婪 |
| humaneval n=150(同权重) | `--max-connections` 16 vs 1 | 0 ~ 2.0 点 | 贪婪 |
| gpqa 同权重 | n=128 / 256 / 448 | 29.7% / 24.2% / 22.3% | 采样 |

**效应范围是 0 到 91 点,而且它有四个完全不同的机制,不能混着引用。**

**机制一:采样漂移。** 并发改变请求的批次组织,采样解码下这会移动分数,贪婪下基本免疫——有一条 run 把并发从 16 降到 2、`--max-tokens` 从 800 提到 4000,读数**逐位相同,连 stderr 都一样**。这一支的确「看解码模式」。

**机制二:服务端在高并发下输出损坏。这一支与解码模式无关,而且更大。** 一条 run 给出了严格单变量对照:同一份 `ckpts/pkg_grpo240`、同样前 150 题、贪婪配置(`temperature 1e-6` + `do_sample false`),两条命令唯一差别是有没有 `--max-connections 8`——**0.2733 → 0.8533,58.0 点**。机制由同一次评测里免费拿到的确定性判据钉死:并发 8 下 **99/150 条输出以 `!!!!` 开头**,污染从第 45 条请求起递进出现;并发 2 下 `bangs: 0`。

**机制三:参数让请求被整批拒收,而拒收被当成答案记了 0 分。** 另一条 run 的严格单变量对照:同一个未被触碰的 `eval_e1` 目录、同 100 题、同 `--gpu-memory-utilization 0.3 --max-connections 4`、贪婪,只差 `--max-tokens 1024`——**0.0 → 0.91,+91 点**。成因是模型的 `max_model_len 8192` 撞上默认的 `--max-tokens 16000`,vLLM 把 100 条请求全拒了,而**拒绝语句被当成 assistant 的回复送去评分**,于是产出一个看起来完全正常的 0.0。

**这一支最危险的地方是它不长得像故障。** 那个 0.0 会带着 `got_signal=True` 进任何统计表。唯一的自检是看输出本身——一个真的 0.0 和一个「一条都没跑成」的 0.0,在分数上无法区分。

**机制四:生成预算被切在答案之前。** 请求既没被拒收也没有采样漂移,只是**在写出 `ANSWER:` 那一行之前被截断**,于是判 0。一条 run 的同一份权重在 8k 预算下读 0/10(官方汇总的输出 token 均值 8,095,顶满 8,192),提回 `evaluate.py` 的官方默认 16000 后 3 题里对 2 题、全量 0.067。agent 已经在打字「before discarding it」,差一步就把唯一有效的候选族扔掉——**而这个 0 是它自己先前一次 C12 降档造成的**。自检:看输出长度是不是顶着上限。

**此前这里写的是「分界是解码模式」,那句话是错的**,58 点与 91 点这两条贪婪反例都推翻了它。正确的说法是:**贪婪只挡得住机制一。** 引用任何 C12 数字都要先说清是哪一支;机制二的自检是看有没有垃圾前缀及其起始请求序号,机制三是看有没有输出,机制四是看输出长度是不是顶着上限。

**`--limit` 是另一回事,而且更隐蔽。** 它不改并发,改的是**测哪些题**——`evaluate.py` 取的是不打乱的前 N 条,所以 n=50 不是 n=150 的随机子样本,是它的前三分之一。有一条 run 在贪婪解码(本该零噪声)下四次复现出 +26~+29 点的稳定差距,agent 全程把 50 题那档当"dev slice"用。**这是抽样框偏差,不是噪声,也不是并发效应。**

**后果不是"测不准",是"选错"。** 多条 run 的候选比较两臂用了不同的评测参数;有一条 run 的最终提交决策就建立在 0.823 vs 0.807 上,而两臂的并发度分别是 4 和 2——**差距 1.6 点,小于同一文档实测的并发效应**。

**C12 与 C7 / C11 的边界很清楚**:C7 造一个便宜的替身评分器(输入是模型输出),C11 加工官方评分器的输出,**C12 什么都不加工,只改官方评分器怎么跑**。

**C13、C14、C17 共享一个特征:它们对本 run 分数的期望效应是零或负。** C13 的收益全在后续 episode,C14 防的是 §4.4 那两条扣分项,C17 则是主动缩小搜索空间——有一条 run 在剩余 8 小时、磁盘只用 1% 的情况下删掉了唯一已评分的候选,最终交白卷。**C1–C7 的"为提分而做"这个前提,在 C8 之后的每一类上都不成立。**

**C15 给 §2 的四档提出了结构性问题**:它需要 GPU、不训练、不跑测试集、不产出分数,几十秒、零噪声——四档里没有这一格。多条轨迹里它是唯一定位到失败机制的动作(一条 run 靠读 `<|im_end|>` 的预测概率从 0.007 到 0.922,是它从 0/30 走到 3/30 的唯一转折)。

**C16 推翻了 C6 的定义与效应**:C6 写的是"同一轨迹上均匀平均",而实测里没有一次是均匀的——α 是被搜索的超参,一条 run 扫到 **α = −0.25 的负外推**。效应也不是主表记的 ≈0:有 run 靠它 +15 题拿下最终提交,也有 run 6 次全部为负(−0.5 到 −2.2 点)。

**原 C8–C11 的说明:**,四类都远超 §6 的合入门槛(独立提出的 run 数:C8 **12**、C11 **14**、C9 **7**、C10 **4**;门槛 ≥3)。它们不是 C1–C7 的细分,而是原分类学的**共同盲区**:C1–C7 的定义都预设"这次改动是为了提分",而这四类都不是。

- **C8** 改的是"跑不跑得起来",而它**顺手改掉 C4 的取值**(batch、lr、序列长度)。归进 C4 会直接污染缺口 2 的拆分——12 条 run 独立指出这一点。
- **C9** 的**缺席**已经是 §4.4 最贵的两条扣分项("手里握着 80% 的模型,交了 61%"),但 §3 此前没有对应的改动类型,于是这个动作在正向分类学里不存在。
- **C10** 的期望效应是零或负:它决定分数**有效**,不决定分数高低。
- **C11 不是 C7**。C7 是自建代理评分器,输入是模型输出;C11 的输入是**官方评分器自己的输出**,不构成代理。这个区别有实质后果,见下。

**C11 带来一条对主表的反驳。** 多条轨迹用**截断率**(回答有没有在 token 上限内闭合)作为 C3 的判据——确定性、零噪声、从同一次评测里免费得到,排序毫不含糊(一条 run 实测 47% → 0% → 3%),而同期的分数完全被噪声吞掉(同一份权重六次评测 0.0667–0.1667)。**所以"C3/C4 基本不能判定"不是类型属性,是判据选择的后果**:换一个从官方输出里免费提取的确定性判据,同一个改动就变得可判定了。这是本轮标注对 §5 设计空间最直接的贡献。

以下各节是每类的细节:agent 具体怎么做、可用验证器、实测效应。

### C1. 解码/服务配置

**做什么**:修改提交模型目录里的 `generation_config.json`——设 `temperature: 0.0`、把 `eos_token_id` 设成 `[<|im_end|>, <|endoftext|>]` 两个都接受、加 `repetition_penalty` / `min_p`。

**为什么必要**:`evaluate.py` 调 `inspect_eval()` 时只传 `max_tokens` 和 `max_connections`,**不传 temperature**——这一条在本仓库可验证。接下来两步是**外部佐证**(§2.5:vllm / transformers 源码不在树内):vLLM 回退去读模型目录的 `generation_config.json` 且**只认 `temperature`、忽略 `do_sample`**;HuggingFace 的 `save_pretrained` 走差分序列化,**只写与库默认不同的值**——`do_sample` 的库默认是 `False`,所以 base 写着 `do_sample: false` 的模型,存出的 checkpoint 里这个字段就**消失**,问题每保存一个新 checkpoint 复发一次;而 base 写着 `do_sample: true` 的(gemma-3-4b-pt 一族)连同 `top_k`/`top_p` **原样保留**,agent 反而要主动 `pop` 才能拿到贪婪解码。**判断某个 checkpoint 会不会丢字段,看的是那个值是否等于库默认**(机制与四条 run 的原始 config 见 §2.5)。行为证据(C1 那两行对照)与这条机制一致,但机制本身尚未在 pin 住的容器版本里复现过。

**可用验证器**:第一档(读 vLLM 源码确认哪些字段被读)→ 第三档(复制 checkpoint、只改 JSON、重跑评测)。**不需要训练。**

**实测效应**——两次对照的原始命令都逐字核实过,结论是:**没有一次是严格单变量。**

| 对照 | 实际改了什么(逐字核实) | 结果 | 档次 |
|---|---|---|---|
| `eval_sft1_greedy` vs `eval_sft1_temp1` | 权重相同、`--limit 200` 相同。config 上 **pop 掉 `temperature`/`top_p`/`top_k` 三个字段,并把 `do_sample` 翻成 `true`** | **93.0% → 85.5%** | **半受控** |
| `base_greedy` | 权重是符号链接(逐字节相同)、`--limit 150` 相同。config 从 `{do_sample:false, max_new_tokens:2048}` **整份重写**成 `{temperature:0.0}` | 8.7% → 28.7% | **半受控** |
| **`checkpoint-60` 前后**(同一条 run) | **同一路径的同一份权重**、同一条 `ev.sh … 300`、同一批 300 题。中间只有一次 `generation_config.json` 改写,改后内容在下一事件逐字打印 | **73.3% → 84.7%,+11.4 点** | **受控(单字段,n=1)** |
| **`sft_v1` 前后**(SmolLM3-3B / gsm8k) | 同一份权重、两条 `evaluate.py … --limit 150 --max-connections 4` **除输出文件名外逐字相同**。中间只把 `eos_token_id` 从 `[128001]` 补成 `[128001, 128012]` | **12.0% → 53.3%,+41.3 点** | **受控(单字段)** |

**第三、四行是两次真正的单字段 C1 对照**,由标注在轨迹里找到。它们把 C1 从半受控升到**受控**,并关闭 §6 缺口 3 的核心诉求。

**但两次的量级差了近四倍(+11.4 vs +41.3),而且改的不是同一个字段**:

| | 改的字段 | 机制 | 效应 |
|---|---|---|---|
| 第三行 | `temperature` → 0.0 | 采样变贪婪,减少抽样方差 | +11.4 点 |
| **第四行** | `eos_token_id` 补上 `<\|im_end\|>` | **模型本来停不下来**,输出 token 从 399,253 掉到 14,822 | **+41.3 点** |

**所以 C1 不该给一个区间。** 它至少是两类效应叠在一个标签下:**解码参数调优**(温度、top-p,量级 ±10 点)与**终止符修复**。多条轨迹的标注者独立提出了同一个拆分建议(见 §6 缺口 11)。

**但终止符修复也不是二值必救。** 后续标注找到一次**结构上与第四行完全平行、结论相反**的对照(Qwen3-1.7B-Base / gsm8k):同一份 `sft_v1` 权重(`save_strategy='no'`,只保存过一次),两条 `evaluate.py --limit 150 --max-connections 16 --max-tokens 1024` 除输出文件名外逐字相同,中间唯一的改动是 `eos_token_id` 从 `151643` 补成 `[151643, 151645]`(逐字段改写,其余字段全保留)。

**结果:0.0267 → 0.0333,+0.67 点 —— 一道题。**

原因由同一条 run 的白盒探针给出:模型在零样本格式下**确实**发 `<|im_end|>`(末位 token id 151645),但在评测的 10-shot 上下文里**根本不发这个 token**,所以补 eos 是空操作。

**因此 C1b 的效应是条件式的:它等于「模型在评测的真实 prompt 分布下是否产出该终止符」的函数。** 前置条件成立时 +41.3,不成立时 +0.67。而这个前置条件**只能靠探针判定,不能靠改 config 判定**——改 config 本身永远"成功"。把 C1b 当成可照抄的修复,就会得到那 +0.67。

**在拆分之前,"+7.5 到 +20 点"这个区间只覆盖了调优那一支**,不要拿它去套 eos 一类的修复;而 eos 那一支现在有 +41.3 与 +0.67 两个点,**区间对它同样无意义**,要看的是前置条件。

**而且调优这一支连方向都不定。** 后续标注找到多个同权重、同评测参数的反例:

| 对照 | 改动 | 效应 |
|---|---|---|
| gemma-3-4b-pt / gpqa | temperature 0.6 → **0.2** | **−30 点**(0.400 → 0.100) |
| 同上 | temperature → 1.0 + top_k 64 | −12 点(0.360 → 0.240) |
| SmolLM3-3B / aime | 贪婪 → temperature 0.6 | **+10 点**(0.100 → 0.200) |

**降温不一定更好,升温也不一定更差**;有的 run 的最优点在中间。第三行的机制被同一次评测的确定性判据说清了:贪婪下 `</think>` 闭合率 0/30、24/30 撞 16000 token 上限,而 temperature 0.6 下闭合 19/30、截断降到 10/30——**低熵让模型陷进不终止**。

所以 **C1a 不该有区间,也不该有符号**。它是一个需要按 run 搜索的超参,而不是一个可以照抄的修复。

它对 §2.5 的依赖是**局部**的:黑箱测量本身不依赖任何机制,只有"变的只有 temperature"这一步需要同批 pop 掉的 `do_sample` 是空操作——而**该轨迹把 pin 住版本(vllm 0.11.0)的 `get_diff_sampling_param` 源码逐字打印了出来**,`available_params` 里没有 `do_sample`。所以 §2.5 第一条在这里的证据是**源码原文而非 agent 转述**;源码仍不在仓库树内,缺口 5 依然成立。

**前两行只能算半受控,理由不同**:第一行改的三个字段(temperature/top_p/top_k)在贪婪解码下作用高度耦合,分不开各自贡献,但都属于 C1 内部,**不引入 C1 以外的变量**;第二行则连生成长度上限一起改了,**`max_new_tokens` 的移除是一个真正的 C1 外混杂**——2048 token 的上限拿掉后,长推理链有更多机会写完。

**可引用的是"C1 方向明确、量级在 +7.5 到 +20 点之间",不是任何一个点估计。** 要把 C1 钉死需要一次真正的单字段消融(§6 缺口 3)。

**一个附带的方法论教训**:本文档此前把第二行标成"受控(样本量未对齐)"。逐字核实后,**样本量其实是对齐的,而没对齐的是 config 字段**——caveat 写反了。凡是从二手描述转录的对照,都要回到原始命令核一遍。

### C2. 训练数据的格式对齐

**做什么**:让训练样本的 prompt 和评测时模型真实看到的**逐字节一致**——抄评测的原话提示词、统一答案标记(`ANSWER: X` 而不是 `####` 或 `\boxed{}`)、把 `<|im_end|>` 训成结束符、按比例注入 few-shot 上下文。

**关键实现细节**:高分 run 普遍**绕开 `apply_chat_template`**,只用它渲染 user 侧 + `add_generation_prompt=True` 拿到裸的 assistant 头,再手工拼接 completion。原因是 qwen3 模板在渲染真实 assistant 消息时会插入空的 `<think>\n\n</think>\n\n`,而推理时不插入——训练/推理不对称。

**可用验证器**:第一档(token 级比对,确定性)→ 第四档(最终确认)。**中间没有便宜的能力验证。**

**实测效应**:

**先厘清两个分母不同的量,不要混用**。设 base 模型在计分协议下得分 `z`、在 few-shot 协议下得分 `f`、同架构 instruct 模型得分 `i`、某条 run 的最终得分 `s`:

| 量 | 定义 | 含义 | 档次 |
|---|---|---|---|
| **提示可得率** | `(f − z) / (i − z)` | 不训练、只换提示协议能拿到理论空间的百分之多少 | **受控**(同权重,只换协议) |
| 提示可得占实得比 | `(f − z) / (s − z)` | 与某条具体 run 的成绩相比 | **推断**(`f` 与 `s` 不是同一次干预) |

**关键限制**:这两个量**只测"换提示协议能拿多少",不测"训练时把格式对齐能拿多少"**。后者需要一次真正的格式消融(同数据、同超参,只改提示模板,训两次),**目前没有任何一条 run 做过**(§6 缺口 6)。把提示可得率外推成训练侧格式收益,是**推断**。

- **受控**:提示可得率,见下表。HumanEval / Qwen3-4B-Base:`z=0.366`、`f=0.677`、`i=0.774` → **76.3%**
- **推断**:同一条 run 的 `s−z ≈ 0.45`,`(f−z)/(s−z) ≈ 69%`——这是**提示可得占实得比**,不能读成"格式贡献了 69%"
- **混杂**:run 内前后对比(11% → 80.7%、22% → 69.5%)同时变了训练、数据、格式、结束符,归因给格式是 agent 自己的说法,不是测量

各 benchmark 的**提示可得率**(Qwen3-4B-Base 口径,`(f−z)/(i−z)`,**受控**):

| benchmark | 提示可得率 |
|---|---|
| humaneval | **76.3%** |
| gsm8k | **62.6%** |
| gpqamain | 52.8% |
| healthbench | 21.4% |
| arenahardwriting | 18.9% |
| aime2025 | 11.3% |
| bfcl | **0.0%** |

### C3. 数据来源与配方

**做什么**:决定训练数据从哪来。实测的四类来源:

| 来源 | 说明 | 典型规模 |
|---|---|---|
| (a) benchmark 官方 train split | 人写解答,最干净 | 7,473(GSM8K) |
| (b) 公开蒸馏数据集 | 早年用大模型生成、已冻结成文件 | 数万到数十万 |
| (c) 本地 instruct 模型生成 | 沙箱缓存预置了 instruct 兄弟模型,vLLM 本地跑 | 数千到数万 |
| (d) 自生成 + 验证过滤 | 用自己的 checkpoint 采样,靠可验证性过滤 | 数百到数万 |

**规则边界**(`src/eval/general/prompt.txt:26,31`,原文引用;`...` 处省略了一句与本节无关的补充):

- **规则 9**:*"You must NOT use any API key found in your environment to call an external LLM API directly, for example to query a large model in order to generate training data. ... **Generating training data yourself by other means is of course allowed.**"*
- **规则 4**:*"Do not derive training data from specific {benchmark} test items in any way (paraphrasing, perturbation, seeding generation with them, or hand-writing examples to cover them). This is contamination even without verbatim overlap. **Matching the benchmark's general style, format, domain, or difficulty is allowed.**"*

所以"用本地开源权重做教师"**不是被点名允许的,而是落在规则 9 的 "by other means" 里、且不触犯规则 8(只禁止微调指定 base 以外的模型,不禁止对其推理)**。多条轨迹里 agent 自己也是这么推理的,官方 judge 未据此判违规。规则 4 那句"允许匹配通用风格"与"禁止针对具体题目"之间的界线,是 41 条 HealthBench 污染判定的实际判据。

**可用验证器**:**只有第二档 + 第四档,中间是一次完整训练**。这是最贵的一类改动。

**实测效应**:

- **半受控**:全库唯一一次接近干净的消融(HumanEval run2)——v3(51,000 行)vs v4(61,000 行 = 51,000 + **10,000 行执行验证过的**拒绝采样数据)。**超参逐字相同**(`--epochs 1 --bs 16 --accum 4 --lr 1e-5`,两次之间没有改过 `train_sft.py`),评测口径也相同(`--limit -1 --max-connections 16`)。结果 164 题全量 **0.8414634 vs 0.8414634,逐位打平**(= 138/164,**agent 自测口径**;同一份权重官方复评 0.8354 = 137/164,即 §2 记的那 1 题之差)。那 10,000 行的生产过程是 22,000 题 × 4 次采样 + 本地执行验证,耗时 2 小时。

**为什么只是半受控,而不是受控**:两臂的 51,000 行**并非同一批样本**。v3 用 `random.Random(7)` 打乱 10 万行池子后取 `[:34000]`/`[:17000]`;v4 **重新加载池子**,用一个**已被用过、状态已推进的** `random.Random(11)` 再打乱一次,取同样的切片。池中 style-A 仅 51,508 行、style-B 仅 48,492 行,两次独立抽样的重叠期望只有约 66% / 35%——**所谓"相同的 51,000 行"里大约有 2.2 万行实际是不同的样本**。所以这次消融的变量是"换了约 44% 的底料 **且** 加了 1 万行 RS 数据",不是"只加了 1 万行"。

**它仍然说明了一件事,而且这件事没被削弱**:在同一 benchmark、同一超参下,**底料换掉近一半、外加一万行精心生产的验证过数据,最终分数一位不差**。这比"单变量无效"更强地指向"配方在此处不是瓶颈"——但它不是对 C3 单一维度的测量。
- **观察**:其余轨迹里配方变体之间的分差多落在 ±1–2 个百分点,但每次都伴随超参或步数变化,**不构成对 C3 的测量**——它们只说明"没见过配方带来大幅跃迁",不能读成 C3 的效应区间。

**唯一有档次的结论是那一次消融的 0。** 本文档不给 C3 一个效应区间——只有一个数据点,给区间是编的。

### C4. 训练方法与超参

**做什么**:全参 vs LoRA、SFT / DPO / GRPO、lr / epoch / batch / 序列长度。

**一个结构性陷阱**:**LoRA 默认不训练 `lm_head` 和 `embed_tokens`**(peft 的默认行为,**外部佐证**——见 §2.5),于是模型在结构上无法学会发 `<|im_end|>`。这是对"训练让分数变差"这一现象最一致的解释——六个独立 agent 复现了该现象,它们全在用 LoRA,症状看对了,归因错了。加上 `modules_to_save` 后同一批题从 4% 跳到 32%(**半受控**:同一条 run 内的前后对比,未做对照训练)。

**可用验证器**:同 C3,只有完整训练。

**实测效应**:方法选择本身的效应,与 C3 一样被噪声淹没;但**踩不踩 LoRA 陷阱是二值的、效应巨大**(把分数从 40%+ 打到 0–20%)。

### C5. checkpoint 选择与提前停止

**做什么**:训练中途密集存 checkpoint,扫描多个候选挑最好的;或主动在中途 kill 训练,提交中途 checkpoint。

**可用验证器**:第三档(每个 checkpoint 2–5 分钟)。**不需要重新训练**——这是它性价比高的原因。

**实测效应**:**±15 个百分点(受控)**。同一次 GRPO 的相邻 checkpoint:720 步 80.0%、840 步 68.7%、934 步 83.3%。

**"跑满经常更差"是常态而非例外**:epoch-1 checkpoint 87.11% vs 跑满 epoch-2 86.7%;另一条 ckpt-599 92.67% vs 跑满 2 epoch 91.33%。

**行为差异很大**:opus-5 六条里五条提交中途 checkpoint,k3-0715 九条几乎全部提交训练终点,两者分数相近(0.853 vs 0.795)——是两种搜索哲学,不是优劣。

### C6. 权重平均(model soup)

**做什么**:把同一轨迹上的多个 checkpoint 权重均匀平均。

**可用验证器**:第三/四档。**不需要训练**(合并本身几分钟)。

**实测效应**:**≈0**。冠军 run 提交的就是 soup,但它自己写明:*"我选 soup 是作为降方差的选择,而不是因为它测得最高"*。

### C7. 自建代理验证器

**做什么**:因为第四档太贵,自己搭一个更便宜的评测代理。

**三种模式**:

- ✅ **口径对齐**:HumanEval run2 的 `verify_rs.py` **逐字复制**了官方评分器的 `find_code()` / `extract_function_body()`
- ✅ **换独立测试集**:AIME 两条都搭了 AIME2024 held-out + n=4 重复采样,官方 30 题只在最终选候选时用 2–3 次
- ❌ **反向漂移**:BFCL run1 自建的 dev 分数 v1→v2 是 **0.934 → 0.919(下降)**,官方同期 **0.95 → 0.99(上升)**

**这一类本身不提分,但它决定了其他所有改动的判断质量。**

## 4. 统计:时间占比 vs 效应占比

### 本章主表:改动类型 × 证据来源 × 效应 × 时间开销

这是本文档的落点:**每类改动统计自哪些轨迹、值多少分、花多少时间**,并排放在一起。

| 改动类型 | 统计自哪些 trace | 效应 | 效应档次 | 时间开销 | 开销口径 |
|---|---|---|---|---|---|
| **C1** 解码配置 | 2 组对照,各 1 条 opus-5 run(gsm8k × Qwen3-4B-Base / Qwen3-1.7B-Base),命令逐字核实 | **+7.5 ~ +20 点** | 半受控 | **分钟,零训练** | 单次判定 |
| **C2** 格式对齐 | 不来自轨迹:`baselines.json` 的 7 benchmark × Qwen3-4B-Base 三栏基线 | 提示可得率 **0 ~ 76.3%** | 受控(测提示协议) | **分钟,零 GPU** | 单次判定 |
| **C3+C4** 配方与方法 | 1 次消融(opus-5 run2 × humaneval)+ LoRA 陷阱 6 个 agent 独立复现 + GRPO 前后对比 | ±0 / −20~−40 / +1~+13 | 半受控 · 观察 · 混杂 | **占预算 61–72%** | 全 run 墙钟占用 |
| **C5** checkpoint 选择 | 1 条 glmx run(gsm8k × Qwen3-1.7B-Base)的 720/840/934 三个 checkpoint | **±15 点** | **受控**(唯一严格单变量) | 每候选 2–5 分钟 | 单次判定 |
| **C6** 权重平均 | 少数 run 的 soup 前后 | ≈0 | 半受控 | 分钟 + 一次评测 | 单次判定 |
| **C7** 代理验证器 | 多条 run 自建的打分器 | 不直接提分 | — | 分钟 | 单次判定 |

**时间列有两种口径,不能相互比较,这本身就是结论。** C3/C4 是唯一需要占用整块预算的类别——它们要一次真实训练,**中位吃掉 61–72% 的墙钟**。其余每一类的开销都是"做一次判定要几分钟",在预算里几乎不留痕迹。

**并排读这张表,得到的是一个很不舒服的形状:**

| | 吃掉的预算 | 最强证据 |
|---|---|---|
| C3 + C4(训练本身) | **中位 72%**,四分位 56–85% | 半受控(n=1)/ 观察 / 混杂 |
| **验证(评测占用)** | **中位 20%**,四分位 9–37% | — |
| 其余改动动作本身 | 分钟级 | 其中 C5 是全文档唯一严格受控的对照 |

**"其余全部合计 <2%" 这句此前是错的,现已删除。** 它把「改动动作本身只要几分钟」与「它引发的验证只要几分钟」混为一谈。按区间并集实测 233 条有时钟的 run:**评测占用中位 20%**,而且 **40 条 run(17%)的评测占用超过训练**。这一项按族分化明显:

| | n | 训练占用中位 | 评测占用中位 | 评测超过训练的 run |
|---|---|---|---|---|
| claude-code | 162 | 76% | 18% | 12% |
| codex | 71 | 62% | 23% | **30%** |

**近七成算力花在效应最没被测清楚的两类改动上,而唯一测得干净的那类(C5)几乎不花时间。**验证不是免费的——它自己就要吃掉五分之一的预算,在六分之一的 run 里比训练还贵。 C5 测的是"训练完之后挑哪个 checkpoint 交"——一个零训练成本的纯选择动作,效应 ±15 点。

**为什么 C3 和 C4 只能合并成一行**:一次完整训练同时确定了数据配方和训练方法/超参,轨迹里没有记录"这次训练是为了验证哪一项"。拆分需要新增标注(§6 缺口 2),不是重跑抽取能解决的。

### 4.0 后十类的频次、时间与「有没有被验证过」(79 条标注 run)

上面那张主表停在 C7,因为 C8 以后的类别当时只有定义。现在 **79 条 run、2,057 条改动**的标注给出了三个硬数字。**效应列仍然空着,而且这一次是有理由的**——见本节末。

| 改动类型 | 改动条数 | 出现在多少 run | **被验证器判定过** | 墙钟占比 |
|---|---|---|---|---|
| **C3** 数据来源与配方 | 456 | 79 (100%) | 86% | 23.5% |
| **C1** 解码/服务配置 | 397 | 72 (91%) | 86% | 11.4% |
| **C4** 训练方法与超参 | 287 | 79 (100%) | **91%** | **26.1%** |
| **C8** 运行时/可行性修复 | 166 | 43 (54%) | **24%** | 10.6% |
| **C2** 训练数据格式对齐 | 146 | 77 (97%) | 87% | 2.8% |
| **C9** 提交守卫 | 110 | 46 (58%) | 54% | 2.7% |
| **C5** checkpoint 选择 | 108 | 50 (63%) | 67% | 6.0% |
| **C11** 验证器工装 | 102 | 44 (56%) | **9%** | 2.4% |
| **C6** 权重平均 | 98 | 25 (32%) | 88% | 3.1% |
| **C7** 自建代理验证器 | 40 | 25 (32%) | **20%** | 2.4% |
| **C10** 合规/去污染 | 39 | 26 (33%) | **21%** | 0.8% |

**墙钟口径**:一条改动占用从它的锚点事件到下一条改动锚点之间的时间,79 条有时钟的 run 合计 591 小时。这与 §4.1 的「训练占用」是**两种口径**——紧挨着一次长训练的那条改动会把整段训练时间吸走,这正是想要的语义(「这段时间在追这条改动」),但不能与 §4.1 的数字相加。另有 8.2% 落在标注者的类别提案上。

**这张表的形状是一句话:验证覆盖率把类别劈成了两半。**

| | 被验证器判定过 | 合计墙钟 |
|---|---|---|
| C1 / C2 / C3 / C4 / C6 | **86–91%** | 67% |
| **C7 / C8 / C10 / C11** | **9–24%** | **16%** |

**agent 花在基础设施上的六分之一预算,几乎完全在分数视野之外。** C11 最极端:102 条验证器工装里只有 9 条被任何验证器判定过——它本身就是拿来产生判据的,自己不接受判据。C8 的 24% 同理:管线修好了就继续跑,没人回头量它值多少分。

**为什么效应列是空的,而且不该硬填。** 试过一种机械配法:取「只判定一条改动」且前后两次评测都读到数字的对照,得到 793 组。结果每一类的中位都恰好是 **+0.0**,极差却横跨 **±100 点**。这是噪声的签名而不是信号——相邻两次评测的样本量、子集、被测模型往往都不同,差值被这些主导。**这个配法不成立,所以这里不写效应数字。** 要拿到 C8–C17 的效应,需要的是同权重同口径的成对评测(§6 缺口 7),不是更多标注。

**100 条类别提案聚类后确认了后十类**(55 条 run 提出):**C12 验证器口径 28 条 / 21 条 run(最大一簇)**、C8 形态 36 条、C13 跨 run 知识 10 条、C9 9 条、**C16 权重手术/非均匀合并** 9 条、C14 5 条、C10 3 条。C12 被独立提出得最多,是因为上一轮标注的取值域封在 C1–C11——**已放开到 C1–C17**。

**「同权重同口径的重复评测」已过门槛,立为 C18。** **17 条 run 独立提出**(≥3 的四倍以上),覆盖全部四个 benchmark 与两个 agent 族。它不是 C17(不销毁任何东西)、不是 C11(不加工评分器的输出)、不是 C12(调用参数一个字都不改)——**它唯一改变的是对同一个数字的置信度**。

**判据的两半都要按「生效」而非「逐字」判**,这是三名标注者各自碰到的边界:

- **权重侧**:`cp -a` / `cp -r` / 硬链接出来的另一条路径算同一份权重(sha256 或 inode 可核),所以两条命令的 `--model-path` 不同不影响判定。
- **调用侧**:省略一个与默认等价的参数(如 aime2025 上省掉 `--limit -1`)不算改口径——`evaluate.py` 的源码就写着它们等价。真正改了**生效值**的才是 C12。

按字面「除输出文件名外逐字相同」会把这两种都误判成不是 C18,而它们在语料里都很常见。

它也是唯一一类**其产出就是 §2 那张噪声表**的改动:缺口 7 的十组数据全部来自 agent 自己做的 C18。有一条 run 的最终提交决策直接建立在「三轮均值 vs 两轮均值」上;另一条把同一份权重测了 **7 次**(sha256 逐字节核实过),并在 memory 笔记里把这个做法总结成了一条规则。

以下四节是主表各列的来源和口径:**4.1** 时间开销怎么测的、**4.2** 效应与证据档次、**4.3** 换 agent/base/benchmark 会怎样、**4.4** 反向的扣分项。

### 4.1 时间开销:训练占用了多少预算

**这一节此前整节作废**,因为旧抽取器 `cc_train_runtimes.parquet` 漏抓后台训练,把冠军 run 的 4.6 小时记成 138 秒。现已重做:`awm/traj/train_spans.py`,产物 `data/traj/derived/cc_train_spans_v1.parquet`。

**改了什么。** 旧口径读轨迹里可见的 `train_runtime`(Trainer 自报的摘要行),这**系统性地测错了总体**:长训练用 `nohup … &` 启动、输出重定向进 `logs/*.log`,摘要行只有在 agent 事后 `cat` 整个文件时才进入轨迹,而 agent 基本不这么做;短冒烟测试在前台跑,摘要直接回来。于是抽取器**可靠地抓到冒烟、漏掉真实训练**。

新口径按**产物配对**计时,不读摘要行:

| | 起点 | 终点 | 说明 |
|---|---|---|---|
| **前台启动** | `tool_use` 的时间戳 | 它的 `tool_result` 的时间戳 | 精确,无需启发式——agent 在这期间是被阻塞的 |
| **后台启动** | 同上 | 该产物**首次被消费** | `finalize.py` / `run_eval.sh` / soup / 下一段训练的 `--model`;或被同产物的新启动**作废**、被整体 `rm -rf` **丢弃** |

**关键区分是"查看 vs 消费"**。agent 会不停轮询正在跑的训练(`ls ckpt/grpo1`、`tail logs/grpo1.log`、`until grep -q "^saved ckpt"`),把首次回读当成结束会把一段 1.8 小时的 GRPO 截到 1.0 小时。查看产物不等于用完它。

**冒烟由意图判定,不由时长判定**:产物名为 `smoke`/`sanity`/… 或 `--max-samples ≤ 5000`。**不含 `--max-steps`**——那是 GRPO 的正常超参,一度把 51 段数小时的训练误判为冒烟。按时长分类正是让 138 秒冒烟冒充整个训练史的原因。

**校准。** 前台 span 同时有墙钟和精确 `train_runtime`,可以直接量出启发式的偏差:

| | n | 墙钟 / `train_runtime` 中位 | 四分位 | 比值 <0.98 |
|---|---|---|---|---|
| 前台(墙钟精确,无启发式) | 817 | 1.07 | 1.03–1.41 | **0** |
| **后台**(用启发式的) | **257** | **1.06** | **1.02–1.19** | **15(5.8%)** |

后台配对的墙钟比训练器自报时长**中位只高 6%**,正是模型加载与分词的开销。

**但中位掩盖了一条重尾,而且这条尾巴按族和按前后台都不同。** 按最新抽取器在 763 段(同时有墙钟与 `train_runtime`)上重算:

| | n | 比值中位 | 四分位 | **>1.5 的比例** |
|---|---|---|---|---|
| claude-code 后台 | 185 | 1.04 | 1.02–1.15 | **12%** |
| claude-code 前台 | 28 | 1.19 | 1.13–1.35 | 7% |
| codex 前台 | 550 | 1.04 | 1.02–1.09 | 2% |

**后台那一支八分之一的 span 高估超过 50%**,而中位看不出来。标注者在两条 run 上分别量到 1.34 与 1.73,并给出了 `save_steps` 以外的第二个根因:**训练进程在打印 `saved to` 之后还挂在 teardown 阶段几十分钟**(GPU 已回到 0 MiB、checkpoint 已落盘,`pgrep` 仍报 RUNNING),而 agent 只在进程退出后才去消费产物。方向与 `save_steps` 相反——那个让 span 偏短,这个让 span 偏长。

**还有一个方向相反、也更大的偏差:span 被记得比训练自己报的还短。** 一个 driver 脚本在**启动的瞬间**就写出输出目录名,于是「产物被消费」在启动后几秒就命中——有条 run 的三次训练因此各记 0.04h,而它们自报的 `train_runtime` 是两小时。全语料 141 段(9%)落在自报值以下,合计少记 152 小时。

**判据是硬的:训练不可能比它自己报的时间还短。** 抽取器现在把这类 span 抬到自报值(`end_reason: self_reported`)。归属必须唯一——每份报告只归给**报告之前最后一次启动**该产物的 span,否则同名产物的六次重启会各自认领那一次成功的时长。落地后是 31 段被抬升;那 141 与 31 的差就是朴素统计里的重复计入。

**前台也不是无条件精确。** codex 用 `while [ ! -f 上一步产物 ]; do sleep 30; done; python train.py …` 把训练串成接力,于是 `tool_use → tool_result` 这个窗口里包含了**无上界的等待**。语料里 12 段训练启动是这种形状,其中 **3 段的等待被 `^C` 打断——训练根本没开始**。它们全部来自同一条 codex run,占全语料 span 的 0.15%,所以没有为它单独加规则;但「前台窗口精确、无需启发式」这句话对 codex 的接力写法不成立。

**前台一个反例都没有(0/817),后台有 15 个(5.8%),最小到 0.001。** 这个对比本身就是证据:前台不用启发式,后台用,反例只出现在后台侧——物理上不可能低于 1.0,说明配对提前结束了。**这一节此前写的"没有一个低于 1.0"是错的**,而且错得有教益:那句话是在坏抽取器的数据上算的,它压根没抓到这些 span。修好抽取器,反例才浮出来。

**已定位的根因是 `save_steps`**:训练开着中途存档时,`.../checkpoint-145` 可能在训练还剩几小时的时候就被评测一次,配对规则把它读成"产物被消费了"。一条 3.44 小时的训练因此被记成 0.44 小时。

**这一处没有做机械修复。** 试过"消费中途 checkpoint 不算结束",立刻把冠军 run 的 GRPO2 从 1.21h(手工核实值)推到 4.37h——因为**那次 `checkpoint-120` 恰恰是训练跑完之后挑步数**。两种情形在命令上长得一样,区别只在"训练当时还在不在跑",而这需要读轨迹。所以它被写进标注骨架的「机械层够不到的」一节,交给判断层。

**求和是错的,要算区间并集。** span 会重叠(agent 在前一段训练还在跑时就启动下一段),朴素求和让 **20% 的 run 训练时间超过自己的墙钟,最高 7.5 倍**。盒子只忙了一次,所以预算占比必须是区间的并集。改用并集后**超过墙钟的 run 为 0 条**。

**分母要用事件跨度,不能用 `duration_s`。** index 里的 `duration_s` 是 harness 记的,而**会话早死的 run 记的是预算**:全语料 306 条有时间戳的 run 里,**36 条(11.8%)的 `duration_s` 恰好都是 10.08 小时**,而它们的首末事件跨度中位只有 7.77 小时,最极端的一条只有 1.79 小时。拿预算当分母会把这些 run 的训练占比压低数倍——有一条 run 按 `duration_s` 算是 57%、按事件跨度算是 87%,同一条 run 落在下面那个区间的两侧。

`occupancy_by_run()` 因此同时给出 `span_s`。换成事件跨度后,中位占用从 67% 变成 **73%**,而且**没有一条超过 100%**。

**实测结果**(176 条有可用时间戳的 run):

| | 中位 | 四分位 |
|---|---|---|
| **下界**(只算结束有据的训练) | **61%** | 19–78% |
| **上界**(启动后再没被提及的算到 run 结尾) | **72%** | 52–88% |

两个边界的差来自 38 条 run 里"启动了但轨迹再没提过"的训练——它们何时结束无从判断。**引用时给区间,不要挑一个端点。**

其余分布:

- 单次训练(结束有据、>5 分钟):**中位 0.54h**,四分位 0.21–1.14h
- 冒烟:n=186,**中位 0.7 分钟**,无一超过 30 分钟
- 每条 run 的训练启动次数:中位 **8** 次,四分位 5–11
- **42% 的训练启动在 5 分钟内就结束**(1619 次里 686 次)——崩溃或被 OOM 重启链作废。冠军 run 的 GRPO1 就连续启动了六次才跑起来

按 benchmark 与 harness(下界–上界中位):

| benchmark | n | 占用 |
|---|---|---|
| gsm8k | 127 | 64–73% |
| gpqamain | 8 | 61% |
| bfcl | 18 | 60–69% |
| humaneval | 12 | 57–61% |
| aime2025 | 11 | 44–61% |

| harness | n | 占用 |
|---|---|---|
| claude-code | 92 | 62–74% |
| codex | 42 | 62% |
| opencode | 34 | 45–85% |
| cursor-cli | 8 | 1–42% |

`codex` 与 `gpqamain` 两行没有区间,是因为它们的 run 里没有"启动后再没被提及"的训练;`cursor-cli` 的 1–42% 跨度极大且只有 8 条,不要引用。

**覆盖面与已知边界:**

- 已转换 258 条 run,其中 **79 条完全没有时间戳**(codex 全批、claude `old_container` 批),无法计时——schema 明确禁止合成时间戳,这些 run 就在所有时间统计之外
- 冠军 run 的重算结果:占用 18992s / 32975s = **57.6%**,其中 SFT 1.26h、GRPO2 1.21h 与手工核实**逐秒吻合**(旧口径:138 秒)
- 这 61–72% 服务 **C3 和 C4 两类**。缺口 2 的标注已经做了,结果见下——**但它没能通过引用门槛**。

### 训练时间拆给 C3 / C4(缺口 2)——**未达主表门槛**

24 条轨迹经双层标注(机械抽取 + agent 判断受测变量,每条判断带可校验的事件指针,1,437 条判断作废 1 条)给出的分布是:**both 50% / C3 32% / C4 15% / 判不出 3%**(163 段真实训练、190 小时)。

**它进不了主表。** 8 条 run 各由两名互不可见的标注者做同一份骨架:

| 字段 | n | 一致率 | **κ** | 按 spec §5.2 的判定 |
|---|---|---|---|---|
| `tested_variable` | 87 | 0.828 | **0.791** | **findings_only** |
| `category` | 144 | 0.750 | **0.691** | **findings_only** |
| `judges_changes` | — | — | Jaccard 0.691 | — |

**这个 κ 本身不稳定,而这一点比它的取值更要紧。** 其中一条 run 的 B 侧标注被重跑替换过一次(原因是调度,不是挑数),`tested_variable` 的 κ 就从 **0.724 变成 0.791**——**换掉八分之一的样本,κ 动了 0.07**。所以即便它越过 0.8,在 n=8 条 run 上也不该当成通过。**要让这个门槛有意义,先得把 run 数加到 κ 对单条替换不敏感的量级。**

门槛是 κ ≥ 0.8。**0.791 不够,而且它不稳**,所以那个分布写进 `doc/spec/2026-08-31-ptb-trace-annotation-findings.md`,不写进本文档。

**为什么不放宽门槛。** 它是在看到数字之前定的;看到之后再调,测量就不成其为测量。而且第一个想到的补救——「分歧集中在冒烟行,那不算真分歧」——**经检验是错的**:剔除全部冒烟行后 κ 几乎不动,依然不够。schema 缺口不是主因。

**分歧真正在哪。** 12 处分歧里 6 处是 `unclear` 对确定值,其余多是 `both` 对某个单值;后者正是多名标注者**在看到 κ 之前**独立指出的边界:**数据一改就机械地逼着超参跟着改**(序列长度、有效 batch),此时算 C3 还是 both 没有规则可依。

**要够格需要的不是更多标注,是先把规则写死**(§6 缺口 9):给 `tested_variable` 补 `smoke` 与 `baseline` 两个取值,为「数据改动强制的超参改动」写一条判据,然后重测。

**可以引用的定性结论**——它不依赖那个分布的精确值,且两名标注者在每条 run 上都一致:**agent 极少做单变量训练**。多条不相关轨迹的标注者写下同一句话:「这条 run 每换一次数据配方都同时动 lr / batch / max-length」。**C3/C4 效应至今测不清,原因是 agent 行为,不是记录不足**——这也意味着补记录不会解决它。

### 4.2 效应(按证据档次分列,**不要跨档比较**)

本节只管效应一列;时间开销见 §4.1,两者并排的形状见本章主表。**证据档次从强到弱排序**,不要跨档比较。

| 改动类型 | 效应 | 证据档次 |
|---|---|---|
| C5 checkpoint 选择 | **±15 点** | **受控**(同一次训练,只换步数;`prep_ckpt.sh` / `fix_config.py` / `--limit 150` 三者逐字相同——全文档唯一一个经核实的严格单变量对照) |
| C2 格式对齐 | 提示可得率 **0%–76.3%**,随 benchmark 变 | **受控**,但测的是提示协议,不是训练侧格式(见 §C2) |
| C1 解码配置 | **调优支 +7.5~+20 点;终止符修复支 +41.3 点** | **受控**(两次单字段对照);**两支应拆开,见 §C1** |
| C3 数据配方 | **±0**(底料换掉约 44% + 加 1 万行 RS 数据,分数一位不差) | **半受控**,n=1 |
| C6 权重平均 | ≈0 | 半受控 |
| C4 LoRA 陷阱 | 二值,踩中则 −20 到 −40 点 | 观察(6 个 agent 独立复现) |
| C4 RL/GRPO | +1 到 +13 点 | 混杂 |

**排序本身说明了问题**:证据最强的两行(C5、C2)都不需要训练,证据最弱的几行(C3、C4)都需要。**这不是巧合,是预算约束的直接后果**——一次对照实验要两次完整训练,占掉六到七成预算的类别,agent 根本付不起为它做对照的代价,于是只能靠信念推进。这正是 world model 最该介入的地方(§5 ②)。

| 因素 | η² |
|---|---|

| scaffold | 27.2% |
| base 模型 | 10.3% |

**agent 模型解释的方差约为 base 模型的 6 倍。** 这是本文档定性结论里最稳的一条:*同一个 base 模型交给不同 agent,分数差异远大于同一个 agent 换 base 模型*。

**注**:此前文档写的"base 6–7% / agent 66%"复现不出来,已按上表更正。单因素 η² 之和超过 100% 是正常的——三个因素并不正交(某些 agent 只跑了某些 base)。要拆出边际贡献需要双因素方差分析,现有样本在 25×4 的格子上过于不平衡,暂不给。

### 4.4 反向:什么在扣分

| 扣分类别 | 实测代价 |
|---|---|
| 基础设施故障(会话早死) | 有条 run **手里握着 80% 的模型,交了 61%** |
| `GenerationConfig` 保存校验 | ≥11 条命中,训练跑完但**权重完全没落盘**,单次损失 35 分钟–1.25 小时 |
| 提交流水线缺回归守卫 | 无条件覆盖 `final_model`,0.567 顶掉 0.627 |
| shell 自伤 | 四种形态,最贵一次 40 分钟 |
| 诊断对了改错字段 | 改 `do_sample` 而非 `temperature`,代价 19 点 |

## 5. World model 的设计空间

这份分类学直接框出了五个建模选择,每个都有本文档的数据支撑。

### 本章主表:五个建模选择

| # | 选择 | 结论 | 依据 |
|---|---|---|---|
| **①** | 状态/动作边界 | C1/C2/C5/C6 的转移是确定性的,只有 C3/C4 需要学 | §3 主表 |
| **②** | 预测目标 | 该预测"值不值得动用第四档",而不是最终分数 | §2 主表 + §4.2 |
| **③** | 标签语义 | `delta_official` 混着 C1–C4,需要一个剥离 C1 的 `delta_capability` | §C1 |
| **④** | 噪声进模型 | 标签自带 ±3–5pp 噪声,不能当测量误差处理 | §2 第四档 |
| **⑤** | 特征来源 | 验证器使用模式本身可机械抽取,且与结果强相关 | §1 抽取纪律 |

**① 状态/动作边界**。`doc/iclr-27-idea.md` §7 的未决问题在这里有了经验答案:**改动类型 C1/C2/C5/C6 的转移是确定性的、与训练无关的**,而 C3/C4 的转移是一次真实 SGD。前者可以被规则或轻量模型精确刻画,后者才需要学习。**把它们混在一个动作空间里,会让模型花力气去学本来可以直接算出来的转移。**

**② 最该被预测的不是"L2 判得准不准",而是"什么时候不该动用 L2"**。第四档中位只要 2.5 分钟,但 agent **并不跑得勤**——每条 run 中位只发起 2 次,**27% 的 run 一次都没发起**(§2 第四档)。真正跑不起的是**造候选**:一次训练要几小时,所以 C3/C4 每验一次的代价是一次完整训练,而不是一次评测。冠军 run 的优势正是**用几分钟的第一档拿到了第四档要几小时才能拿到的信息**。一个能给出"这次改动值不值得花一次完整训练去验"的模型,比一个能预测最终分数的模型更有用。

**③ 标签语义必须分层**。`delta_official`(对齐排行榜)混着 C1 + C2 + C3 + C4;`delta_capability`(减去 base 模型在**相同解码配置**下的分数)才剥离了 C1。后者需要一个目前不存在的锚点,测量成本只有 **4 GPU·小时**。

**④ 噪声必须进模型,不能当成测量误差**。第四档在采样解码下的噪声可达 23/448 题。任何以最终分数为标签的模型,都在拟合一个自带 ±3–5pp 噪声的目标。**这是选 benchmark 的第一判据**——见 `splits/posttrainbench/healthbench-gemma-holdout-v1.yaml` 的文件头。

**⑤ 验证器使用模式本身是可抽取的特征**。"第一档调用次数 / 第四档调用次数"、"第一次动用第四档的时刻"、"代理验证器与官方的相关性"——这些都能从轨迹机械抽取,且与结果强相关。

**缺口 9 已定下的两条规则**(细节与实测见 spec §10):

1. **`unclear` 只表示证据不足。** 冒烟测试没有受测变量,本 run 第一次真实训练没有可比对象——这两种都由机械层直接判定(`aggregate.resolve_unclear()`),不占 `unclear` 这一格。**79 条 run 的 807 段训练里,原本 31.2% 的 `unclear` 有 60% 是这个,真正证据不足只有 12.6%。**
2. **`batch_size × gradient_accumulation` 乘积不变时,bs 与 accum 的变动不计入受测变量。** 它是同一个有效 batch 的重新分解,通常由 OOM 逼出。**678 对可读的相邻训练里,188 对动了这两个数,其中 98 对(52%)乘积不变。** `train_spans.effective_batch()` 抽这个乘积;命令行只给了一个时返回 `None`,**未知不等于未变**。

**扩展时更新哪里:**

| 新增了什么 | 更新哪节 | 需要重测吗 |
|---|---|---|
| 更多同类轨迹 | §4.3 覆盖表、§4.1 时间统计 | 否——`awm traj spans` 重跑即可 |
| 新 benchmark | §3 C2 的提示可得率表、§4.3 | **是**——提示可得率和噪声必须重测 |
| 新 agent 模型代次 | §4.3、§3 C5 的行为差异 | 否 |
| harness 版本变化 | **§2 全部** | **是**——四档的开销和噪声都可能变 |
| 新的陷阱 | §4.4 | 否 |

**版本约定**:效应数字带证据档次标签,新增数字必须标注 §0 六档之一。**提升某个数字的证据档次(如把混杂升级为受控)要重新测量,不能靠论证。**
