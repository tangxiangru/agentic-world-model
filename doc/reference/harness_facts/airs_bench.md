## 0. Headline findings (read these first)

1. **The public `aira-dojo` cannot run AIRS-Bench as-is.** `TASK_MAP = {"MLEBenchTaskConfig": MLEBenchTask}` is the only registered task (`$AIRS/aira-dojo/src/dojo/config_dataclasses/task/__init__.py`), `BenchmarkConfig.to_cfg_list()` hard-codes `MLEBenchTaskConfig` (`config_dataclasses/benchmark.py:369`), and `main_run.py:71` does `import mlebench` unconditionally. The only trace of the internal AIRS task class is the help string `"e.g., 'mlebench', 'AIRS-H'"` (`config_dataclasses/task/base.py:25`, `benchmark.py:24`). A grep for `project_description|metadata.yaml|evaluate_prepare` over aira-dojo returns nothing. **VERIFIED.** So Meta's "AIRA-dojo Greedy/One-Shot" AIRS runs used an unreleased `Task` subclass; you would write your own (sketch in §3.5).
2. **The official protocol did *not* use MCTS/evolutionary.** Paper §6 and Table 7: three scaffolds only: One-Shot (= aira-dojo Draft operator once), Greedy (AIDE-style tree search in aira-dojo), ReAct (MLGym). MCTS/Evo solvers exist in aira-dojo but were not run on AIRS-Bench. **VERIFIED** (`$AIRS/airs-bench-paper.txt` lines 659-664, 1833-1856).
3. **The AIRS-Bench task format is harness-agnostic** (`prompt .md` + `prepare.py` + `evaluate_prepare.py` + `evaluate.py` + `metadata.yaml`), and the repo ships a converter to MLGym. The clean integration contract is: prompt = `project_description.md`; agent sees `./data/{train,test}` (read-only); agent writes `./submission.csv`; grader = `evaluate.py` run against `./data/test_with_labels`. **VERIFIED.**
4. **No official run logs/trajectories are public** (GitHub, HF, MLGym repo all checked; aira-dojo issue #12 asking for trajectories is open and unanswered since 2025-12-29). **VERIFIED.**
5. Per-run raw scores of Meta's agents are not released; only `estimated_worst_score` (= s_min) and `sota_score` per task in `metadata.yaml` (confirmed by maintainer in airs-bench issue #6). **VERIFIED.**

## 2. Task definition format

### 2.1 Layout (`$AIRS/airs-bench/airsbench/tasks/rad/<TaskName>/`) — VERIFIED

```
metadata.yaml            # task card: dataset, splits, metric, SOTA, s_min, s_opt, pip reqs
project_description.md   # the agent prompt (verbatim; ends with the evaluate.py source in a ```py block)
prepare.py               # raw HF dataset -> ./data/train (+val) and ./data/test (labels stripped)
evaluate_prepare.py      # raw HF dataset -> ./data/test_with_labels ; copies agent's submission.csv into ./data
evaluate.py              # grader: python evaluate.py --submission-file ./data/submission.csv
utils.py                 # optional shared code (CodeXGlue MRR, APPS, time-series)
custom_labels.py         # optional: builds gold_submission.csv when scoring column needs transformation
testing_util.py          # APPS only (executes candidate programs against hidden tests)
gold_submission*.csv     # only SVAMP committed; .gitignore ignores rad/*/*.csv otherwise
```
A parallel MLGym rendering lives in `airsbench/tasks/mlgym/<TaskName>/{configs/tasks/*.yaml, configs/datasets/*.yaml, data/{evaluate.py,requirements.txt}}`, produced by `$AIRS/airs-bench/scripts/converter_rad_mlgym_enhanced.py`. Validation script: `airsbench/tasks/rad/test_task_folder.py` (runs prepare → evaluate_prepare → evaluate with gold + permuted submissions, checks metric moves and gold = optimum, checks required metadata fields).

**Script contracts (VERIFIED from WinoGrande/U0 files):**
- `prepare.py --global-shared-data-dir <raw HF save_to_disk root> --agent-data-mount-dir <dir bound as ./data> [--agent-log-dir <dir>]`; loads `load_from_disk(f"{root}/{hf_id}/{config}")`, writes `train/`, `test/` (test with scoring column removed; QM9 tasks also write `val/`; U0/G labels ×1000; CodeXGlue writes `<split>/search_corpus`, `<split>/queries_with_labels`, `test/queries`).
- `evaluate_prepare.py` same args; writes `test_with_labels/` and copies `{agent_log_dir}/submission.csv` → `{agent_data_mount_dir}/submission.csv`.
- `evaluate.py --submission-file ./data/submission.csv`, cwd must contain `./data` (test harness symlinks the mount to `./data`); prints `--- EVALUATION RESULT ---` followed by a one-key JSON `{"<MetricName>": float}`; `test_task_folder.py` parses it with regex `--- EVALUATION RESULT ---\s*(\{[\s\S]*?\})`.
- No time/hardware budget lives in the task folder. Only `metadata.yaml` pip requirement lists (`container_python_requirements`, `evaluate_container_python_requirements`, `prepare_code_python_requirements`).

## 3. Harness / agent interface (AIRA-dojo)

### 3.1 Launching — VERIFIED
- Single run: `python -m dojo.main_run +_exp=<name> [overrides]` — Hydra (`@hydra.main(config_path="configs", config_name="default_run")`, `$AIRS/aira-dojo/src/dojo/main_run.py:135`). `default_run.yaml` composes `metadata`, `logger`, `task: ???`, `solver: ???`, `interpreter: ???` into dataclass `RunConfig` (`config_dataclasses/run.py`).
- Sweep: `python -m dojo.main_runner_job_array +_exp=<runner> launcher.debug=False` — expands `benchmark.tasks × vars` (e.g. `vars: metadata.seed: [1..10]`), snapshots the repo, submits one Slurm job per run via `submitit` (`main_runner_job_array.py`). Slurm only (`launcher/slurm.yaml`: 1 node, 1 GPU, 24 CPUs, 200G, `time: "36:00:00"`, matching Table 7's "24h, up to ~36h incl. evaluation").
- Example exp config `configs/_exp/mlebench/aira_greedy_o3.yaml`: `override /interpreter: jupyter`, `override /solver: mlebench/greedy`, `override /benchmark: mlebench/lite`, per-operator client overrides `override /solver/client@solver.operators.draft.llm.client: litellm_o3` (analyze uses `litellm_4o`).

### 3.2 Isolation — VERIFIED
- `interpreter: jupyter` → `JupyterInterpreterFactory` → `ApptainerJupyterServer` (`core/interpreters/jupyter/apptainer_jupyter_server.py`) → bash wrapper `core/interpreters/jupyter/sand`, which runs:

  with `APPTAINER_BIND="<data_dir>:/root/data:ro,<read_only_binds>"`. Agent code runs in a Jupyter kernel via kernel-gateway; each `step_task` starts a **fresh kernel** (`reset_session=True` default), `fetch_file()` pulls `submission.csv` out through the kernel. No network namespace flags → internet allowed (Table 7: "Internet access: Yes, HF_HUB_OFFLINE=1 by default but agent can flip it"). `sand` assumes Slurm (`$SLURM_JOBID`, `/scratch/slurm_tmpdir`); override `TMP_BASE_DIR` otherwise. Superimage: `superimage/apptainer.def` (nvidia/cuda:12.4.1-ubuntu22.04, Miniforge, PyTorch cu12.4, RAPIDS 25.02, faiss-gpu, jupyter-kernel-gateway, sshd on 17022); build `apptainer build --fakeroot …sif apptainer.def` (`docs/BUILD_SUPERIMAGE.md`); `configs/interpreter/jupyter.yaml` sets `superimage_version: "2025-05-02v2"`, `env: {HF_HUB_OFFLINE: "1"}`.
- `interpreter: python` → `PythonInterpreter` (`core/interpreters/python.py`): local `multiprocessing` child with `exec()`, no isolation, `./data` symlinked. Debug only.

### 3.3 Solver / operators / search policy — VERIFIED
- Registry: `SOLVER_MAP = {GreedySolverConfig: Greedy, MCTSSolverConfig: MCTS, EvolutionarySolverConfig: Evolutionary}` (`config_dataclasses/solver/__init__.py`); dispatch is by config dataclass class name (`utils/config.py:build`).
- Operators = LLM calls with Jinja prompts: `draft`, `improve`, `debug`, `analyze`, (`crossover` for Evo) in `core/solvers/operators/*.py`, configured in `configs/solver/operators/mlebench/{aira_operators,aide_operators}/*.yaml` (each has `llm.client`, `generation_kwargs`, `system_message_prompt_template`, `input_variables`). `analyze` uses function-calling schema `submit_review` → `{is_bug, summary, metric}` (`operators/analyze.py`).
- Greedy loop (`solvers/greedy/greedy.py`): `search_policy()` → draft until `num_drafts`, else with prob `debug_prob` debug a buggy leaf (depth ≤ `max_debug_depth`), else improve `journal.get_best_node()`; each step: operator → `execute_op_plan_code` (extract plan + single ```python block) → `task.step_task(state, code)` → `parse_eval_result` (LLM analysis → `metric`, overridden by `validation_fitness` if the task returns one; `is_buggy` if `is_bug` or exit_code≠0 or metric None or `valid_solution` False) → `journal.append`; stops at `step_limit` or `time_limit_secs`; returns `(state, best_node.code, best_node)`.

### 3.4 The task/agent boundary — VERIFIED
- `Task` ABC (`core/tasks/base.py`): `prepare(**task_args) -> (state, task_info)`, `step_task(state, action) -> (state, outcome)`, `evaluate_fitness(...)`, `close(state)`. `task_info` keys: `task_description`, `lower_is_better`. Outcome keys (`core/tasks/constants.py`): `execution_output` (`ExecutionResult{term_out, exec_time, exit_code, eval_return, timed_out}`), `validation_fitness`, `valid_solution`, `valid_solution_feedback`, `test_fitness`, `aux_eval_info`.
- `Solver` ABC (`core/solvers/base.py`): `__init__(cfg, task_info)`, `__call__(task, state) -> (state, solution_code, best_node)`, plus `save/load_checkpoint`. `main_run.py` then reads `best_node.metric.info["score"]` as final fitness (raises if absent).
- **The action is one self-contained Python script string** (`MLEBenchTask.step_task` does `extract_code(action)` then `interpreter.run(solution, file_name="solution.py")` in a fresh kernel, grades `submission.csv`, deletes it from the workspace). There is no "agent gets a shell" abstraction; the interpreter accepts `!cmd` shell lines inside kernel code but it is a Jupyter kernel, not a PTY, and the task resets/closes it per step.

### 3.5 Plugging in your own agent (e.g. a Claude-Code-style shell agent)
Option A — inside aira-dojo (**what it would require**, VERIFIED against the code):
1. Write `AIRSBenchTask(Task)` (none exists): in `__init__` read `project_description.md` (+ optionally `metadata.yaml`); `prepare()` runs `prepare.py --agent-data-mount-dir <task.data_dir>` (that dir is bound RO at `/root/data`), returns `{task_description, lower_is_better: metadata.metric_lower_is_better}`; `step_task()` executes the script, `fetch_file(submission.csv)`, runs `evaluate_prepare.py` + `evaluate.py` on the host/eval container, parses the JSON → `test_fitness`/`aux_eval_info["score"]`/`valid_solution`. Add `AIRSBenchTaskConfig(TaskConfig)` in `config_dataclasses/task/`, register in `TASK_MAP`, add `configs/task/airsbench/<Task>.yaml`; patch `BenchmarkConfig.to_cfg_list` (hard-coded `MLEBenchTaskConfig`) and the `import mlebench` sanity check in `main_run.py` (or install mle-bench).
2. Write a `Solver` subclass + `SolverConfig` dataclass + `configs/solver/<name>.yaml`, register in `SOLVER_MAP`; drive your agent inside `__call__`, keep the persistent kernel with `interpreter.run(code, reset_session=False)` (or `"!bash -c ..."`), and at the end return a final script that regenerates `submission.csv` (the task re-executes it in a fresh kernel). Log nodes with `self.logger.log(journal.get_node_data(i) | {"current_best_node": k}, "JOURNAL", step=i)` if you want the tree tooling. A shell-native agent fits this poorly (Jupyter kernel ≠ TTY, per-step reset).

Option B — **recommended**: skip aira-dojo, consume the task folders directly (this is exactly what the MLGym path does; the MLGym task YAML uses `task_entrypoint: CSVSubmissionTasks`, `starter_code: [evaluate.py]`, `evaluation_read_only: true`, `use_separate_eval_container: true`, `training_timeout: 3600`, `eval_timeout: 3600` — `$AIRS/airs-bench/airsbench/tasks/mlgym/CoreferenceResolutionWinograndeAccuracy/configs/tasks/*.yaml`, VERIFIED). ## 4. Scoring — VERIFIED (paper §5.2 + repo)

- **Raw score** `s`: `evaluate.py` on the hidden test split (`./data/test_with_labels`, produced by `evaluate_prepare.py`) → single metric. Invalid/missing `submission.csv` → invalid run.
- **Normalized score** (README + paper Eq. 2-3): `NS = (φ(s) − φ(s_min)) / (φ(s_sota) − φ(s_min))`, `φ(s) = −log10(|s − s_opt|)`; `s_min = metadata.logging_info.estimated_worst_score` (worst score over all seeds/agents observed by Meta; confirmed in issue #6), `s_sota = sota[0].sota_score`, `s_opt = optimal_score`. Failed/invalid runs count as NS = 0 when averaging over seeds; NS > 1 means SOTA beaten. Appendix B also reports an identity-transform variant. Other metrics: valid-submission rate (Eq. 1) and Elo via Bradley-Terry over pairwise per-task comparisons incl. "SOTA" as a player (Eq. 4-5). **No normalization/aggregation code ships in the repo** (only `notebooks/create_summary_plots.ipynb`; the "run_benchmark.py/aggregate_results.py" mentioned by a web summary do not exist — VERIFIED absent).
- **Where the grader lives**: `airsbench/tasks/rad/<Task>/evaluate.py` (harness-independent). In aira-dojo the grading call would live in the task's `step_task` (as `MLEBenchTask` does with `mlebench.grade`), i.e. **every node is scored on the test set** (Table 7 "Every solution scored on test set: Yes" for AIRA-dojo; MLGym scores only the final submission).
- **Intermediate validation signal**: the agent's own printed validation metric (prompts demand 5-fold CV and printing it), extracted by the `analyze` LLM operator into `node.metric`; search selects by this (`use_test_score: false`), test score is stored in `metric_info/score` but unused for selection. Final reported score = test score of the best-by-validation node (`main_run.py:116-124`).
- Leaderboard (README): Greedy gpt-oss-120b 0.402±0.031 (10 seeds) … One-Shot Devstral 0.018 (20 seeds); MLGym ReAct CWM 0.302. Runs: 24h, 1×H200, ≥10 seeds (paper §5.1).

### 5.1 What aira-dojo writes per run — VERIFIED
Output dir `{LOGGING_DIR}/aira-dojo/user_{USER}_issue_{metadata.git_issue_id}/{id}/` (`config_dataclasses/logger.py:627`; docs give `{id}` = `user_{USER}_issue_{ID}_seed_{SEED}_{run_hash}`):

- `{exp_name}_{ts}_Greedy_search_data.json` (`{"nodes": [...], "solution": <best code>, "config": {...}, "tree_path"}`) and `{...}_tree.html` (D3 tree, `core/solvers/utils/tree_export.py`)

Node 0 is an empty root (`code=""`, `is_buggy=True`, `WorstMetricValue`).
**LLM messages are captured**: each `operators_metrics[i]` = `{"usage": {prompt_tokens, completion_tokens, total_tokens, latency, success, cost, cumulative_num_llm_calls}, "prompt_messages": [{role, content}…], "completion_text": str}` (`GenericLLM.__call__`, `core/solvers/llm_helpers/generic_llm.py:900-950`; stored via `Node(operators_metrics=[metrics])` in `greedy.py:264-266` and appended by `_analyze`).

## 6. Complications for running it yourself

1. **Data**: 16 HF datasets, none gated (HF API, VERIFIED). Repo storage upper bounds: monash_tsf 24.5 GB (only 3 configs needed; loader script pulls per-config zips — actual size UNVERIFIED), apps 11.4 GB, duorc 9.7 GB, code_x_glue 8.4 GB, yelp 7.2 GB, eli5 6.0 GB, finqa 0.5 GB, ZINC 265 MB, qm9 150 MB, super_glue 103 MB, sick 43 MB, squad 16 MB, SVAMP 13 MB, winogrande 4.4 MB. Download uses `datasets==3.6.0` with `trust_remote_code=True` (`datasets/prepare_hf_datasets_text.py`), while task containers pin `datasets==4.0.0` (metadata) — mismatch also noted in paper Table 7 ("3.5.1, upgrade to 4.0.0"). Downloading the eight GPU-heavy tasks needed **both** pins, not either (OBSERVED, 2026-08-25): `datasets==3.6.0` cannot read `rajpurkar/squad` at all, because its features use the `List` type that only exists from 4.x, and 4.x removed `trust_remote_code`, which the older loaders still need. SQuAD was fetched with 4.1.1 and everything else came from the 3.6.0 venv through upstream's own download script.
2. **Pretrained-model cache**: official runs had 193 HF checkpoints pre-cached (paper Appendix E, newest deberta-v3-large 2021) with `HF_HUB_OFFLINE=1` default but internet allowed; the cache is not distributed. Reproducing exactly needs a similar cache + proxy env (`RAD_HTTP_PROXY`, `RAD_HF_TOKEN` pass-through in `sand`).
3. **Compute**: 1×H200 + 24 CPUs + 200 GB RAM per run, 24h search (+ up to 36h wall), 4h per solution execution; official scale = 20 tasks × 10-20 seeds × 14 agents. One agent config ≈ 4,800 GPU-hours at 10 seeds. Paper Table 8 lists "Budget/Cost: not specified".
4. **Infra assumptions**: Apptainer (fakeroot, `--nv`), a custom multi-GB superimage build (RAPIDS, faiss-gpu, PyTorch cu12.4), Slurm/submitit for sweeps, `sand` hard-codes `/scratch/slurm_tmpdir/$SLURM_JOBID` and `/shared/cache/dojo/tasks/mlebench` path rewriting; `install_mlebench.sh`/mle-bench (with a manual one-line patch) required even for non-MLE tasks. MLGym-side configs hard-code `data_path: /checkpoint/maui/shared/datasets/airs_text_only_prepared/<Task>` — regenerate with the converter.
5. **LLM backends** (`core/solvers/llm_helpers/backends/utils.py`, VERIFIED): `api ∈ {litellm, openai, gdm}`. `LiteLLMClient` prefixes the model with `azure/` or `openai/` only → OpenAI, Azure OpenAI, or any OpenAI-compatible endpoint (vLLM/self-hosted via `base_url`, e.g. `configs/solver/client/default_litellm.yaml`, `litellm_r1.yaml`). `GDMClient` = Gemini (`GEMINI_API_KEY`). **No Anthropic client** — `anthropic==0.49.0` is in `requirements.txt` and `FunctionSpec.as_anthropic_tool_dict` exists, but nothing routes to it; you'd patch `LiteLLMClient.__init__` to use an `anthropic/` prefix (or point `base_url` at a proxy). Keys: `PRIMARY_KEY_<MODEL_ID_UPPER_WITH_UNDERSCORES>` else `PRIMARY_KEY`. `analyze` relies on function calling (falls back to text). Retries: 10, timeout 1500 s per call.
6. **Evaluator drift**: four evaluator fixes merged Apr-May 2026 (ELI5 ROUGE-1→ROUGE-L, SQuAD/DuoRC answer normalization, MASE constant-series skip). Paper Appendix G still names the task `QuestionAnsweringEli5Rouge1`; repo folder is `QuestionAnsweringEli5RougeL`. Whether the leaderboard was recomputed: UNVERIFIED (README "Date 2026-02-16" predates the fixes).
7. **Security**: `CodeGenerationAPPSPassAt5/evaluate.py` executes the agent's 5 programs per problem against hidden tests (`utils.evaluate_all_testcases`, `testing_util.py`, needs `pyext`) — grade in a sandbox. WebTraffic MASE over 145k series is slow.
8. **Docs rot**: README points to `src/dojo/configs/run/solver/client/…` (real path `src/dojo/configs/solver/client/`, issue #10); airs-bench README names `download_hf_datasets_text.sh` (real: `download_hf_datasets.sh`) and links a mistyped task folder.
