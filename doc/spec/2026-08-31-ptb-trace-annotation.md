## 1. 目标

`doc/reference/verifier_tiers_and_change_types.md` 现在的效应列建立在极小的 n 上:C1 靠 2 组对照,C3 靠 1 次消融,C5 靠 1 条 run 的 3 个 checkpoint。§6 列了 8 个缺口,其中最大的一个是**训练时间拆不开**——61–72% 的预算服务 C3 和 C4 两类,而轨迹里没有记录"这次训练在验哪一项"。

这项工作交付三个相互依赖的结果:

1. **一份可计算的标注表**,覆盖 180 条轨迹的每一次训练、每一次验证、每一次改动,每个字段都带回原始事件的指针。
2. **§6 缺口的关闭**,首先是缺口 2(把训练时间拆给 C3 / C4),其次是把主表里"半受控 / n=1"的格子换成有 n 的数字。
3. **world model 的特征与标签**。标注 schema 按 `doc/reference/...` §5 的五个建模选择倒推设计,所以关闭缺口的同一次标注,直接产出建模要用的状态、动作与转移记录。

**一个明确的非目标**:这不是"让 agent 读 trace 写总结"。见 §3。

- 附加层用于**覆盖面描述**与 benchmark 间对比(同一 benchmark 内部,base 分布是平的)。
- `arenahardwriting` 只有 2 条,**仅登记不参与任何统计**。

合计 **180 条**(claude-code 126 / codex 54)。

**healthbench 是本 spec 新增拉取的**。原因如下。

**为什么原本不在**:`awm/traj/fetch.py` 的默认 fetch 只取 `PTB_CORE_BENCHMARKS`(aime2025 / gsm8k / gpqamain / humaneval / bfcl),两个 LLM 评判的 benchmark(healthbench、arenahardwriting)要显式 `--observe` 才拉。所以本地一条 healthbench trace 都没转换过。

**为什么必须补**:实验目标 split `splits/posttrainbench/healthbench-gemma-holdout-v1.yaml` 正是 healthbench。**split 是计分契约,只需要 catalogue 里的分数与 judge 判定,一条 trace 都不依赖**;标注需要 trace。两种数据需求不重叠——所以那份 split 当初 `apply_rule` 0 issue 通过,而它的 150 条 run 本地只有 2 条有 `solve_out.txt`。不补的话,我们会标注五个 benchmark,然后在一个从未看过的第六个上跑实验。

已补:本 spec 六个模型 × healthbench = 64 条,pin 到与 split 相同的 revision `39d3fcd794df51c062c8bd3b7f8523ba707aaeb3`,0.1 GB,16 个 experiment 各 4 条。其中 1 条(`codex_non_api_xhigh_gpt-5.5_10h_run2__healthbench_Qwen_Qwen3-4B-Base_17391825`)**事件流不带时间戳,已剔除**,故 healthbench 计 63 条。

### 2.3 两个族必须分开统计

| | claude-code | codex |
|---|---|---|
| 事件数中位 | 888 | 498 |
| run 时长中位 | 9.3h | 2.1h |

**不得把两族合并成一个总体报数。** 行为形态差一倍以上,合并出来的中位数不描述任何真实的 agent。所有聚合统计按族分列;跨族对比是结论之一,不是统计口径。

### 2.4 规模

180 条 run 合计:

- **233,277 个事件,47,294 次工具调用**
- **1,456 次真实训练启动**(其中 1,085 次结束有据)+ 180 次冒烟
- 每条 run 中位 7 次训练

## 3. 机械层与判断层的分界

**这是本 spec 最重要的一条约束。**

上一轮的经验是明确的:这份 reference 文档里被推翻的五处数字(45% 时间占比、C1 两组对照的"受控"标签、方差分解、全量评测耗时、C3 消融的"同数据"),**没有一处是靠多读几条轨迹发现的**,全部靠回到原始命令逐字重算才抓出来。所以"让 agent 大规模读 trace 然后汇总"这个动作,放大的是同一类错误,而不是把它平均掉。

因此:**凡是脚本能确定性抽出的字段,一律不进 agent 的任务。**

| 机械层(脚本,确定性,可测试) | 判断层(agent,脚本答不了) |
|---|---|
| 训练区间:起止 / 时长 / 产物 / 结局(`awm/traj/train_spans.py`,已完成) | **每次训练的受测变量是 C3 还是 C4**(缺口 2) |
| 验证事件:`--limit`、`--max-connections`、时刻 → 档位 | **每次验证在判定哪一次改动**(改动 ↔ 验证器的链接) |
| 验证事件是否真的返回了可用数字(结果文本里有没有 accuracy) | 每次改动归到 C1–C7 哪一类 |
| `generation_config.json` 的字段级 diff | 分类学本身的缺口(见 §6) |
| 工具调用计数、文件编辑、最终分数、judge 判定 | |

机械层的字段**不占验证预算**,因为它们由测试保证;判断层的字段全部需要 §5 的可采信性机制。

这条分界也决定了 agent 任务的形状:agent 拿到的不是原始事件流,而是**机械层已经填好的骨架 + 原始事件流**,它只填空。输出量因此小一个数量级,也更容易查。

### 3.1 需要新增的机械抽取

`train_spans` 已完成。还需两个,都在 `awm/traj/` 下,都按同样的标准写测试:

两个模块都已建成并带测试。实现过程中各自撞到一处**机械层拿不到的东西**,都已按 §3 的分界移交判断层,并如实记录在下:

| 模块 | 抽到了什么 | 机械层拿不到的 |
|---|---|---|
| `awm/traj/eval_events.py` | 每次 `evaluate.py` / `run_eval.sh` 调用:时刻、`--limit`、并发、被评模型、验证器档位、**是否有分数关联回来** | **`got_signal` 是下界,且松紧程度两族不同** |
| `awm/traj/config_writes.py` | 每次读/写 `generation_config.json` 的事件位置、访问类型、**内容(拿得到时)** | **字段级 diff 做不了** |

**`got_signal` 的边界。** False 只表示"追不到分数",不等于"agent 什么都没学到"。实测:claude-code 70% 能关联上,codex 53%。差距是**取回方式**的差异而非认知差异——codex 习惯用自己写的分析脚本去读 inspect_ai 的时间戳日志(`analyze_eval.py logs/2026-07-17T01-32-28+02-00_gpqa-main_<hash>.json`),该文件名无法从启动命令预测。已排除竞争解释:未关联的结果里**没有一条**被轨迹截断,且平均 26 kB 的 vLLM 日志,分数确实不在启动事件的输出里。已追四条通道(请求的输出文件、命令行上的日志、被评 checkpoint 名、后台任务 id),此外"这次评测有没有让 agent 学到东西"是判断题。

**字段级 diff 为什么做不了。** 约 1,500 次触碰 `generation_config.json` 的事件里,**只有 41 次带可解析内容**(claude-code 的 `Write` 29 次 + shell heredoc 12 次),**codex 为 0**——codex 把文件改动发布成 `file_change` 事件,只有路径和 `kind`;主流写法是 python heredoc 里的 `json.dump`,是任意代码。执行它们既不安全也不可复现。所以模块只做**定位**:告诉 agent 该读哪几个事件,字段级差异由 agent 读那段 heredoc 得出。这不是妥协,正是分界线在起作用。

**两处不对称都要带进结论**:任何跨两族比较的 C1 结论,比的是"部分解析的记录"与"全靠阅读的记录"。

去重:两个模块都按事件去重,不按命令文本——后台任务靠轮询取结果,按文本计数会把一次评测重复计成 3–5 次。

## 4. 标注 schema

三张表,主键都指回 `(run_id, i)`。

### 4.1 `changes` — agent 做的每一次有意图的修改

| 字段 | 类型 | 来源 |
|---|---|---|
| `run_id`, `i` | 锚点事件 | 机械 |
| `category` | C1–C7,或 `proposed:<slug>`(见 §6) | **判断** |
| `summary` | 一句话:改了什么 | **判断** |
| `evidence` | `[(i, 原文片段)]`,至少一条 | **判断** |

### 4.2 `trainings` — 每次训练在验什么(缺口 2)

以 `train_spans` 的每一行为单位,**1,456 行**。

| 字段 | 类型 | 来源 |
|---|---|---|
| 全部区间字段 | 起止 / 时长 / 产物 / kind / end_reason | 机械(已有) |
| `tested_variable` | `C3` \| `C4` \| `both` \| `unclear` | **判断** |
| `vs_previous` | 与上一次训练相比,具体改了什么;首次训练为 `baseline` | **判断** |
| `evidence` | `[(i, 原文片段)]` | **判断** |

`unclear` 是**合法且必要的取值**。逼 agent 在证据不足时二选一,是在制造假数据;`unclear` 的比例本身就是一个要报的数字。

### 4.3 `verifications` — 每次验证在判定哪次改动

| 字段 | 类型 | 来源 |
|---|---|---|
| `run_id`, `i`, `tier`, `n_samples`, `got_signal` | | 机械 |
| `judges_changes` | `change_id` 列表,可为空 | **判断** |
| `outcome_read` | agent 从中读到了什么(数值或"未拿到") | **判断** |

`judges_changes` 是多对多:一次改动可能先过静态检查再上局部评测,一次全量评测可能同时裁决多个候选。**这张链接表就是 world model 的状态转移结构**,也是本次标注唯一必须靠判断的核心产物。

## 5. 可采信性

三重,逐层收紧。

### 5.1 指针校验(全部,机械)

每条判断记录的 `evidence` 至少一条 `(i, 原文片段)`。校验脚本检查:

1. 该 `i` 在这条 run 的事件流里存在
2. 该片段**逐字出现**在那个事件的命令或文本里

任一不成立即整条记录作废并重标。这不保证判断正确,但机械地排除了编造位置——而编造位置正是 agent 汇总最常见的失效形态。

### 5.2 双标注(20%,度量)

随机抽 **22 条 run**,按族分层保持比例:**claude-code 15 条、codex 7 条**。由第二个 agent 在**不看第一份标注**的情况下独立标一遍(它拿到的输入与第一遍逐字相同)。报字段级一致率:

| 字段 | 指标 |
|---|---|
| `tested_variable` | Cohen's κ(四类) |
| `category` | Cohen's κ(C1–C7 + proposed) |
| `judges_changes` | Jaccard(链接集合) |

**这些一致率决定判断层字段能进哪个证据档次**,按 `doc/reference/...` §0 的六档:

- κ ≥ 0.8 → 可作**观察**档引用,可以进主表
- 0.6 ≤ κ < 0.8 → 只能写进 findings 文件,主表里标注"标注一致性有限"
- κ < 0.6 → **该字段作废**,连同基于它的结论一起。不改口径重标就不发表

没有一致率数字,agent 标出来的"受测变量"撑不起 C3/C4 的拆分——这正是要花那 20% 的原因。

### 5.3 已知锚点(回归)

以下已手工核实的事实,新流程必须复现,否则先修流程再跑全量:

| 锚点 | 期望 |
|---|---|
| 冠军 run 的 SFT / GRPO2 时长 | 1.26h / 1.21h(逐秒) |
| 冠军 run 的 GRPO1 重启链 | ≥4 次 superseded |
| `base_greedy` 的 config 改动 | 三个字段,含 `max_new_tokens` 被删 |
| C3 消融两臂的超参 | 逐字相同;数据不同(RNG 种子 7 vs 11) |

## 6. 分类学的演化通道

C1–C7 是从一批具体轨迹归纳出来的,**它一定不完整**。180 条跨两个模型族的轨迹里出现分类装不下的改动,是预期而非异常。

因此 agent **被明确授权**提出三类修正,但都进入待审队列,不自动合入:

| 提案类型 | 记录什么 | 合入门槛 |
|---|---|---|
| `proposed_category` | 装不下的改动、证据指针、建议的类别定义与边界 | **≥3 条 run 独立提出同一类**,且不与现有类重叠 |
| `definition_defect` | reference §1–§3 里某条定义与轨迹不符,附反例指针 | 单条反例即可进入审阅 |
| `boundary_case` | 落在两类之间、按现定义无法判定的改动 | 累计 ≥5 条则触发该边界的重新定义 |

`definition_defect` 的门槛之所以是"单条反例即可",是因为定义缺陷是**证伪**——一个反例就够了。这一轮的 `base_greedy` 就是例子:文档写着"受控(样本量未对齐)",逐字核实后发现样本量本来就对齐,没对齐的是 config 字段,caveat 整个写反了。

审阅由一次独立 pass 完成,合入 reference §1–§3 时必须同时更新 §6 的维护表。

## 7. 执行形状

### 7.1 分批,每批都是决策点

**不要一次性把全部 agent 打出去。** 三批,前一批不过就停:

| 批次 | 规模 | 目的 | 不过就停 |
|---|---|---|---|
| **批 0** | 4 条锚点 run | 验流程能否复现 §5.3 那四个手工核实的事实 | 复现不了先修流程,不往下走 |
| **批 1** | 20 条试点,**含全部 22 条双标注** | 测 κ 与 `unclear` 比例;检验 schema 是否够用 | κ < 0.6 就改 schema 重来,而不是烧完剩下的 |
| **批 2** | 其余 | 全量 | |

最坏情况的损失是批 0 + 批 1 ≈ 46 次调用,而不是全部 203 次。

### 7.2 调用总数与并发是两回事

- **一条 run 一个 agent**,输入是该 run 的事件流 + 机械层已填好的骨架,输出是 §4 三张表里属于这条 run 的行
- 双标注的 22 条与第一遍**同输入、不同 agent 实例、不共享上下文**
- 审阅 pass 1 个,读 §6 的待审队列给出合入建议

| | 数量 |
|---|---|
| 主标注 | 180 |
| 双标注 | 22 |
| 审阅 | 1 |
| **调用总数** | **约 203** |
| **建议并发** | **8–16** |

**调用总数不是并发数。** 并发取 8–16 是为了中途可叫停、便于观察前几条的输出质量;把它调高只影响墙钟,不改变成本或结论。

两族分别跑,提示词共用同一份 schema 定义,**不为某一族定制**——两族的差异是要测的结论,不能先写进提示词里。

findings 文件是**详情记录,不是 reference**:reference 说方法论和结论,findings 说这 180 条轨迹各自发生了什么。两者的关系是"结论 ↔ 原始记录",任何人应当能从 findings 里的某一条追回 reference 里的某个数字。

每条 run 一节,固定六个小节,顺序不变:

| 小节 | 内容 |
|---|---|
| 元信息 | run_id、模型、harness、benchmark、base 模型、时长、最终分、judge 判定 |
| 改动序列 | `changes` 表按时间排,每行带类别与证据指针 |
| 训练序列 | `trainings` 表,含区间、受测变量、与上次的差异 |
| 验证序列 | `verifications` 表,含档位、样本量、**是否拿到信号**、判定了哪些改动 |
| 结局 | 交了哪个产物、分数从哪来、与 base 的差 |
| 异常与存疑 | `unclear` 的训练、未拿到信号的验证、§6 提出的分类学问题 |

按 (族, benchmark, 模型, run_id) 排序,便于并排比较。

**规模**:**166 / 168 条 run** · 5,574 条改动 · 1,609 段训练 · 3,050 次验证。`tested_variable` 分布 both 22% / C3 21% / C4 19% / smoke 17% / baseline 11% / **unclear 7%** / C2 3%。

**差的 2 条是**`…opus-4-8_10h_run2__gsm8k_Qwen_Qwen3-4B-Base_17349934` 与 `…__gsm8k_google_gemma-3-4b-pt_17325000`(批次收尾时仍在标注,未回)。**人群因此不是满的**:它们都是 claude-opus-4-8 run2 的 gsm8k 格,该格其余条目已覆盖,所以缺口不改变任何按族或按 benchmark 的结论,但引用「168 条」时要知道实际是 166。

**第 3 条不达标是本次最重要的输出。** 它意味着缺口 2 的分布(both 50% / C3 32% / C4 15%)只能停在 findings 文件里。门槛是在看到数字之前定的,没有事后放宽;而最顺手的补救(「分歧都在冒烟行,不算数」)经检验是错的——剔除全部冒烟行后 κ 几乎不动。

**分歧的真实位置**:多名标注者在看到 κ 之前就独立指出同一个边界——**数据一改就机械地逼着超参跟着改**(序列长度、有效 batch),此时算 C3 还是 both 无规则可依。所以下一步不是加标注量,是先写规则(§10)。

**这一轮真正的产出不在 κ 上,而在机械层**:标注者报回的每一处定义缺陷都带可核对的反例,累计修掉 20 余处抽取错误——包括 51 段幽灵训练、141 段被记得比自报时长还短的 span(152 小时)、55 个假评测、以及 12 条 reprompt run 里 404 条被覆盖的命令。**这些修复改变的数字比标注本身多。**

## 10. 下一步(按依赖排序)

1. ~~**给 `tested_variable` 加 `smoke` 与 `baseline` 两个取值**~~ —— **已做**。六名标注者独立报了同一件事,而这件事根本不需要判断:机械层本来就知道哪段是冒烟、哪段是本 run 第一次真实训练。`aggregate.resolve_unclear()` 按这两个事实改写,已标注与待标注的 run 因此站在同一口径上,无需返工。

 结果:**79 条 run、807 段训练里,原本 252 段 `unclear`(31.2%)有 150 段是 schema 装不下(60%)**,真正证据不足只剩 102 段 = **12.6%**。分布变成 both 33.1% / C4 19.1% / C3 16.6% / unclear 12.6% / smoke 12.0% / baseline 6.6%。

2. **为「数据改动强制的超参改动」写判据** —— **判据已定,且可机械判定**。

 **规则:若 `batch_size × gradient_accumulation` 的乘积不变,则 bs 与 accum 的变动不是受测变量。** 它们只是同一个有效 batch 的重新分解,通常由 OOM 逼出。四名标注者各自报了这个形状(`bs 4→2` 配 `accum 4→8`),都因为无处可归而记成超参改动。

 **语料实测:678 对可读的相邻训练里,188 对动了 bs 或 accum,其中 98 对(52%)乘积不变。** 一半以上的「超参改动」根本没改优化器看到的那个数。`train_spans.effective_batch()` 抽这个乘积;命令行只写了其中一个时返回 `None`——**未知不等于未变**,调用方不得当作未变。

 序列长度的对应判据尚未定:`max_len` 随数据长度调整同样是补偿,但没有一个类似「乘积」的守恒量可查,留待下一轮。

3. **重测 κ:拆分后 κ=0.793(原 0.791),几乎没动。** 这个结果本身是信息:拆分修正的是 `unclear` 的**含义**,不是标注者之间的一致性——他们本来就都把冒烟填成 `unclear`,同改同不改。剩余 13 段分歧集中在 C3/C4/both 之间(6 段),正是上面第 2 条判据要管的地方,但这 8 条 run 里没有一段是乘积守恒的实例,所以判据在这个样本上无从生效。仍是 `findings_only`,且 n=8 支撑不起门槛判定——换一条 run 就动 0.07。
4. **给 C8–C11 补效应与时间统计** —— **频次与时间已补(reference §4.0),效应仍空,而且是有理由地空**。频次、run 覆盖率、墙钟占比都在表里了;顺带量出一个没人要的数字,反而是最有信息量的:**验证覆盖率把分类学劈成两半** —— C1/C2/C3/C4/C6 有 86–91% 被验证器判定过、占 67% 墙钟;C7/C8/C10/C11 只有 9–24%、占 16%。

 效应列**不填**:试过的机械配法(取「只判定一条改动」且前后都读到分数的对照,793 组)给出每类中位恰好 **+0.0**、极差横跨 **±100 点**——这是噪声的签名,不是信号,因为相邻两次评测的样本量、子集、被测模型往往都不同。要拿到 C8–C18 的效应,需要的是缺口 7 那种同权重同口径的成对评测,**不是更多标注**。
